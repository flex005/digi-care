# CLAUDE.md — diGi-Care

Rules that hold in every session. Read `FRONTEND_PRD.md` for the full spec; this file is the short list that must never be violated, whatever the task looks like.

**Project:** diGi-Care — care management platform, desktop manager app, frontend only. No backend, no API, no auth. All data from typed fixtures in `src/data/`.

**Scope — who this platform is for.** diGi-Care Admin & Manager is the **only** product in this repo, and its users are the governance roles: the Admin and the Manager. **Care Worker, Family Portal and Super Admin are separate products with their own PRDs and their own UIs.** They are not views of this one and they are not built here.

The distinction that keeps getting re-derived wrongly, so it is written down once: **a role can appear in this product as a subject without being a viewer of it.** An Admin invites care workers, assigns them, deactivates them and reads what they recorded — so care workers appear throughout Team Management, the activity log, every author byline and the permission matrix. None of that makes them users of this platform. Before putting a role somewhere, ask which of the two it is: *somebody who signs in here*, or *somebody this product holds a record about*. Only the first belongs on the sign-in screen, and only the first can be the reason a branch exists.

**Stack:** Vite 8 · React 19 · TypeScript strict · React Router 7 (data router API) · Radix primitives (hand-authored) · plain CSS + CSS Modules over custom properties · `vite-plugin-svgr`.

---

## 1. The Evidence Invariant — the rule this product exists to protect

**A blank must never be able to mean either "no" or "nobody has looked yet".** In a regulated care record those are opposites. Everything below follows from that.

- **No clinical or compliance status is optional.** Every one is a closed discriminated union with an explicit unrecorded member. No `status?:`, no `| null`, no `| undefined`, no default parameter standing in for a missing record. The compiler must reject a screen that forgot the unrecorded case.
- **Unrecorded gets the hatched treatment** (`--status-unrecorded`, dashed border, diagonal hatch) plus visible text saying what is missing. Never empty space. Never a solid neutral fill. Never a RAG colour.
- **A compound state renders as separate facts.** Given-but-no-second-signature is a green "Given" pill *and* a hatched "Second signature not recorded" — two facts, two treatments. Never merged into one pill with the gap in small print.
- **Recorded and unremarkable renders quietly.** A completed in-date review, "nothing due", "all assessed" — plain text, not a filled pill. Quiet is not hidden: the full record still shows, author and timestamp included. Never reach for this to calm down a *gap*.
- **A claim over a filtered set carries the filter, or it is false.** A gap marker inside "Medication notes only" asserts an absence that is an artefact of the view. Suppress the claim or name the filter.
- **A recorded negative is not an unrecorded value.** "Not Given — resident refused — signed 08:04" is a complete record and looks settled. An omission looks unfinished. Never the same treatment.
- **Every aggregate carries its denominator.** No bare counts, no bare percentages, anywhere. Use the `Aggregate` type. Where coverage is too thin to support a claim, render **Insufficient Evidence** — which is not a milder Red, it is the absence of a finding.
- **Absence from a list is the same bug as a blank cell.** All nine risk assessment templates are listed even if none is completed. All eight consent types. All ten care plan domains. (Nine, not ten: the Mental Capacity Act two-stage test left the risk assessments in Phase 5 as a recorded departure, because it is a capacity determination and not a risk, and forcing it into a union whose job is to produce a risk level would make it say something it does not say. This line said ten from Phase 3 until Phase 17, which is the staleness entry in §8 happening to the file that contains it.)

If you find yourself writing a fallback like `?? 'Low risk'`, `|| 'None'`, `?? 0`, or `?? '—'` for anything clinical or compliance-related, stop. That fallback is the bug this product is being built to prevent.

## 2. Wrong-subject writes

- Every write surface carries a persistent, non-collapsing subject header: resident photo, name, preferred name, room, DOB.
- Subject identity comes from the route parameter. Never from navigation history, "last viewed", or component state.
- Confirmation dialogs name the subject in the sentence. "Record 08:00 medications for Emmanuel Okafor?" — never "Are you sure?".
- Active site name is always visible in the header, including for single-site users.

## 3. Icons

- **No icon library. Ever.** Do not install `lucide-react`, `react-icons`, `@heroicons`, or any equivalent, for any reason, including "just for this one icon".
- Icons come from the Aligned Line Icons set in `src/assets/icons/<CATEGORY>/` (3,559 SVGs, ~40 category folders). Never hand-edit those files.
- **Names are namespaced by category** because filenames repeat across folders: `<Icon name="add-remove-delete/add-01" />`, not `<Icon name="add-01" />`.
- Build step normalises used icons to `currentColor` so they take colour from CSS, then SVGR compiles them.
- `npm run icons` generates both `registry.names.generated.ts` (full name union, types only) and `registry.generated.ts` (import map of **only the icons actually used**, found by scanning source). Importing all 3,559 would bloat the bundle.
- **Never hand-type, hand-edit, or hand-extend either generated file.** A name not present in the folder fails the build.
- Re-run `npm run icons` after using a new icon name. It is wired into `predev`/`prebuild`.
- One `<Icon name="..." />` component. No raw `<svg>` in feature code, no direct imports from `src/assets/icons`.
- If a needed icon is not in the folder: **stop and ask.** Do not substitute an inline SVG, an emoji, a character glyph, or a similar-looking icon.

## 4. Colour and type

- **Colour only from tokens.** No hex, `rgb()`, `hsl()`, or named colours in any component. Colour reaches a component only as `var(--token)`. `src/styles/tokens.css` is the single exception and the only place a literal may appear.
- Stylelint enforces this and must stay in CI and pre-commit. Do not disable, weaken, or add exceptions to that rule.
- **Each status has a bright fill token and a darker ink token.** `--status-X` is for fills, dots, bars, borders and icons. `--status-X-ink` is for text on a tint. Using the fill token for text fails contrast and is a review blocker.
- **The type scale is closed.** Nine steps, five weights, all in `tokens.css`. No component introduces a size, line height or weight outside it. A tenth step is a conversation, not a local override.
- No dark mode. One palette. Do not add theme switching, `prefers-color-scheme`, or a `.dark` class.
- Spacing is the 4px scale only. No off-scale values.

## 5. Primitives

- **Do not run the shadcn CLI.** It installs `lucide-react` and overwrites the stylesheet with its own tokens — both break rules above. This is known; it does not need rediscovering.
- Primitives are hand-authored in `src/components/primitives/`, thin wrappers over Radix, styled to our tokens from the first line.
- Reading shadcn source as a reference for Radix composition is fine. Copying its stylesheet, token names, or dependencies is not.

## 6. Conventions

- **One shape, one meaning.** Underline strip = navigation. Pill = filter. Two concepts in one treatment is the same defect as one concept in two; "they never appear on the same screen" is not a defence, because a reader learns the shape rather than the screen.
- **Segmented control = one of a small set of mutually exclusive presentations of the same data.** Week/month on the MAR chart is an instance, not the definition; calendar/list on the activities week is another. Widened deliberately rather than adding a fourth shape.
- **A value whose correct rendering depends on where it appears cannot be rendered by whoever happens to be appending it.** It gets one owner, and the call site asks that owner. Six so far, each found the same way — `quantityWithUnit` (stock, depends on the count: "1 patches"), `pluralise` (a plain count: "1 days"), `scoreText` (a union member: "[object Object]"), `INCIDENT_TYPES.phrase` (a label that reads correctly in a column and wrongly in a sentence: "the fall — witnessed of 23/08"), `formatLateness` (how overdue, depends on the size: "426 days late"), `formatAttributionOn` (who and when, depends on how old the record is: a draft from last Tuesday rendered as "11:29").
  "1 patches" and "1 days" were each written twice in independently authored files — not typos, but what happens when a formatting rule has no owner, and the second occurrence proves there will be a third. **The last is the sharpest**: time alone is correct for a record read on the day it was made — a dose at 08:04, a note from this shift — and every use of it until this one was that kind of record. A rule that was right for every case it had met is the hardest kind to notice going wrong.
  **The tell, twice now: a test that has to be relaxed to let a correct change land was pinning the rendering rather than checking the property.** `/days overdue/` asserted the *unit* in order to check that a duration was stated at all.
- British English in code and UI copy. `Organisation`, `Authorised`, `Finalise`.
- Dates `DD/MM/YYYY`, times 24-hour. Relative time only alongside an absolute timestamp, never instead of it.
- **Clinical timestamps render in the site's timezone, never the viewer's.** Show the zone label where ambiguous. Relative time is the exception — it is about now, not the record.
- Every clinical record shows its author and timestamp. Always visible, never hover-only.
- Care notes are immutable after submission. There is no edit control. Corrections create a new linked note.
- No `any`. No `@ts-expect-error` without a comment naming what removes it.
- No `localStorage` / `sessionStorage` for record data. In-memory only.
- No placeholder or lorem text. No `console.log`. No commented-out code.
- Fixtures stay messy on purpose — missing assessments, omissions, thin sites. Do not "clean up" fixture data to make a screen look better. The gaps are the test.

## 7. Accessibility

- WCAG 2.2 AA. Colour never the sole carrier of meaning. Visible focus ring, never removed.
- The MAR grid is a real `<table>` with header associations and full-sentence accessible names per cell.
- Icons are `aria-hidden` unless labelled. Icon-only controls need a visible adjacent label or an `aria-label` plus tooltip.

## 8. Standing checks

These have each caught a real defect more than once. Run them rather than rediscovering them.

- **Every state a component can render needs a fixture that reaches it.** `latestNote: 'none'` shipped in three places for a resident who could not exist; "All assessed — no flags" went dead silently; the `on_file` photo branch was never rendered. If no fixture reaches a branch, either the fixture is wrong or the branch is.
- **An assertion you edit each phase to make it pass has stopped asserting.** A hardcoded count of disabled nav items measures the work, not the rule. Derive it from the declaration.
- **A comment claiming a guarantee is a claim to verify, not documentation.** Ten were found overstated in one sweep — each named a real mechanism that enforced something narrower than claimed. The ones that held had a test behind them.
- **Volume that drowns a distinction is the same failure as a blank cell.** 303 omissions where three were specified; a chip that fires on every row; markers on half a timeline. Check the count, not just the rendering.
- **A fact you intend to derive is only derivable if the record keeps what it is derived from.** `ReviewState.completed` carried the date a review was done and the date the next one falls due, and not the date it *had been* due — so "reviewed on time" and "reviewed three weeks late" were the same record, and the lateness was not hidden but absent. **And what it is compared against may not exist**: a review nobody ever scheduled can still be done, and it had no deadline to beat. Inventing one produces a lateness nobody can check, so the field is a union — a date, or a statement that there was never one. Same shape as a controlled drug count with no opening balance: the comparison has two inputs, and the missing one is a state rather than a zero.
- **A clamp or conversion written for one kind of instant will silently corrupt another.** `dueBy` is a deadline, `signedAt` is a signature, `recordedAt` is an observation — all three are `IsoDateTime` and the compiler cannot tell them apart. A helper that exists to stop a *signature* landing in the future, applied to a *deadline*, dragged every post-incident review flag back to this instant: the whole set read as overdue and the constant named `FLAG_STILL_IN_TIME` was not still in time. That is the reassuring-branch problem in reverse — it manufactured an alarm rather than hiding one, and a false alarm on every row costs the same as a hidden gap, because both teach the reader to stop looking. **The tell: before applying any transformation to a timestamp, say out loud what kind of instant it is.**
  **This entry is no longer the mechanism either.** It sat here from Phase 7 and the class landed three more times: `filedOn` widened to midnight and rendered through the site's zone as "02/10/2025 01:00 BST", and a review's `dueOn` doing the same on the Dashboard — "01:00 BST" against every overdue review on the screen. So `scripts/check-instant-kinds.mjs` enforces the half of it that is mechanical: a date widened into an instant by string concatenation is a finding **unless it is consumed by `new Date(` on the same line**, which is arithmetic. `// instant-ok: <why>` opts out per site and the count is printed. It does not catch the original clamp — a function applied to the wrong kind of instant is not a string shape — and saying so is part of the entry: **the tell still has to do the work for that half.**
- **Fixtures may be wrong on the facts, not just thin.** One to three care notes a day is not a patchy home, it is a home that does not exist. Correcting a wrong baseline is not tidying up gaps — the deliberate gaps stay exactly as they are.

- **What has already happened to this record before somebody opens this screen?** The fixture check above covers states of a component; this covers states of the record a screen edits — part-recorded, recorded by somebody else, superseded. On any screen more than one person touches, part-recorded is the ordinary state and empty is the rare one, so a suite written entirely against empty is testing the exception. A dose already signed for once rendered as an empty control, inviting a second signature over somebody else's name.
- **An assertion that has to be relaxed to make a legitimate change was testing the wrong thing.** "Exactly three omissions in the whole set" was asserting a property of the home in order to check a property of a fixture. Hold the specified case by reference, never by a number that legitimate data would move.
- **An assertion written from the same string or the same assumption as the code confirms the bug rather than catching it.** The "4 hours threshold" wording, and the round's `balance - 1` arithmetic, were each asserted from the same mistake they contained. Assert the behaviour, not the literal you just typed.
- **An assertion satisfied by an equality is not asserting a margin.** `flagIsOverdue` is `dueBy < now`, which is false when the two are equal — so a review flag with *zero seconds left* counted as one somebody could still do on time. The guard was green and the fixture had no in-time flag in it at all. Where a test means "with room to spare", it has to say so: a boundary is the one place a broken mechanism and a working one give the same answer.
- **A proxy for a rule is a second rule, and two rules drift.** A test asked a hand-written approximation of the "all assessed, no flags" condition — four of the six things the cell actually checks — and the approximation stopped being satisfiable while the real condition still was. **It failed on a screen that was working**, which is the direction that gets working code changed to satisfy a broken test. It drifts the other way too, and then it passes while the branch it protects goes dead; the failure looks different each way round while being the same defect. The fix is the same in both directions: **assert through the thing itself**, never a hand-written approximation of it. Export the predicate the screen uses and have the guard call it.
  **A second occurrence, from the other end: reproducing a rule is the same defect as approximating one.** The Dashboard needed to know which days a drug falls due on, so the helper was written by reading the fixture generator and restating its arithmetic — faithfully, except for a `Math.min(…, 89)` clamp, one token, that anchors the schedule to the first day on the chart rather than to the prescription date. Two counts of the same doses today, 162 and 163, from two functions written minutes apart. Neither was obviously wrong and nothing failed; what found it was printing both numbers next to each other. The generator now exports the constant and both sides read it — a copied formula is a second rule even when it was copied correctly, because the original is still free to move.
- **Any test whose result derives from `now` gets a pinned instant and a sentence saying why, when it is written.** Not after it fails. This has caught the same class three times: green all day, red at 04:42, and in one case the screen was right and the assertion was wrong. The cost is one line; the failure mode is a suite that is green for you and red for whoever runs it next, which reads as flakiness and gets retried rather than read.
- **A suite that goes green on the first run of new tests deserves a look at whether the tests can fail.** Three times now this instinct has found something. `expect(after.items.length).toBeGreaterThan(0)` was asserted on the *unpatched* fixture — true before the act it was testing and after it. `rows.length % 10 === 0` is true of ten, of twenty, and of zero. Neither could fail, and both read as coverage. Pick the two or three assertions carrying the most weight and break the code under them on purpose.
- **A query must name the element it means, specifically enough that nothing else can satisfy it.** `queryByRole('button', { name: /Acknowledge/i })` matched the "Not acknowledged" filter pill; `container.querySelector('ul')` matched the profile header's risk flags list; `container.querySelector('[data-state="recorded"]')`, meaning the allergies badge, took whichever badge a fixture shift put first. The polarity was never the point — a **positive** assertion reaching for a loose selector fails in the more dangerous direction, passing on the wrong element rather than failing on the right one.
  **This entry is no longer the mechanism.** It sat here from Phase 4 and did not prevent a single one of the recurrences, so `scripts/check-selector-specificity.mjs` enforces it in both polarities: a query rooted on the document or on `container` in a router test must be scoped to an element the test chose, or name its target with an attribute selector, an exact string, an anchored pattern, or three words. `getBy`/`findBy` are exempt because the library already throws on an ambiguous name; an un-indexed `…All…` query is exempt unless it claims the sweep found nothing. `// selector-ok: <why>` opts out per site and the count is printed.
  **The general rule, and it applies to every entry here: a standing check that has not prevented a recurrence after three tries is not a check, it is a note.** Either it becomes enforceable or it stops being counted as coverage.
- **One class here is uncovered, and is written down as uncovered rather than given a mechanism that reads as coverage.** A selector naming a *condition* where the test meant an *identity* passes the check above, because it does name an attribute: `container.querySelector('[data-state="recorded"]')`, meaning the allergies badge, is specific and still wrong. Deriving condition attributes from the source — those emitted with two or more distinct literal values — separates `data-state` and `data-finding` from `data-badge` and `data-field` correctly, and then calls `data-tally-cell="invited"` a condition, which it is not: there the condition **is** the identity of the cell. That produced 85 findings with legitimate cases among them, and a guard needing 85 escape comments is wallpaper inside a week — the exception-list failure named two entries above, arrived at from the other direction. The tell is the whole defence: **before selecting on an attribute, say whether it names which element or what condition it is in.** If it is the condition, the query takes whichever element the fixture happened to put first.
- **Knowing an entry does not inoculate you against it.** The Dashboard's date-kind guard asserted that *at least one* row rendered a date, while every review on the screen was widened to an instant — the unsigned handovers satisfied it. That is the specificity defect wearing a positive, written minutes after the entry describing it, by the person who had just written that entry. **Familiarity is not the defence; the mutation is.** Break the code a guard was written for and watch it fail, every time — a guard that passes on the defect it exists to catch has not been tested, however well its author understands the class.
  Four occurrences now, and the fourth adds a mechanism the other three do not have. `check-assignment-reach` shipped with a dead-entry check that could not fire, written in the same hour as the entry about assertions that cannot fail. An audit for guards reporting activity rather than coverage committed that defect inside itself. Both are the shape above: the author knew, and the knowing did not reach the act.
  **The fourth is different, and it is the one that says where a warning belongs.** `residents.ts` generates from one seeded stream, and it carries a warning saying so: *"Not hoisted: `makeCarePlan` draws from the same stream, and moving the draw earlier would shift every fixture after it."* That warning was read during the phase that then broke it — a new `gender` draw inserted beside `pronouns`, where the field belongs on the record, shifting every subsequent draw and leaving two residents with a communication need written in pronouns they do not use. The knowledge was present, correctly filed, and attached to `makeCarePlan`. The case arrived at `gender`.
  So the line is not familiarity. It is that **a warning attached to one instance does not protect the class, and the only reliable place for it is where the act happens** — the reasoning now sits at the draw rather than at the top of the file, which is the one place somebody adding a draw will read it.
  And what caught it is the other half of the same point: **a pronoun guard failed on a change that had nothing to do with pronouns**, and nothing in the diff pointed at it. That is the whole value of a guard over a warning. **A warning is read by whoever happens to look; a guard fires at whoever happens to break it.**
  **A fifth, and it is the entry turned on a conversation rather than a file.** Phase 23 was agreed, then skipped: the next message was Phase 24, and when asked whether 23 was done it was confirmed on the word of whoever had said they would build it. The git history went from Phase 22 to Phase 24 with nothing between, visible the whole time and consulted by nobody. **A plan agreed in conversation and a commit in the history are different facts, and only one of them is evidence.** "Done" is a claim about the history, so it is checked there — `git log` between the last two phase commits — before it is believed, the same way a deploy is checked against the bundle rather than the push.
- **Ask whether a value means anything without the thing beside it, not whether the field is present.** The admission form asked what somebody is allergic to and what happens, and `Allergy` had always required a severity — so "rash and swelling" was not a field somebody forgot, it was **a fact with its other half missing**, and it reads as complete because both words are there. A presence check finds nothing here; the question that does is whether the value can be acted on alone. It could not: the difference between mild and anaphylaxis is whether that person carries an adrenaline pen. **The same test finds the next one** — a dose with no unit, a score with no band, a count with no denominator, a negative with no source.
- **Rendering everywhere is not coverage.** A value on six screens looks proven by its ubiquity and is the most likely thing in the build to be unasserted, because nobody writes a test for something they see constantly. "(deactivated)" rendered beside authors in six modules and exactly one test touched it — a unit test on the formatter, not a screen. Changing where it came from altered twenty-three files and broke nothing. **The tell is a change that touches many files and breaks nothing: that is not confidence, it is silence.** When a refactor comes back green faster than it should have, go and find what was supposed to have caught it. **Second occurrence, one phase later**: the sidebar alert told every screen that "the Reviews module arrives in a later phase" for nine phases after Reviews shipped. Nothing caught it, and nothing could have — it was true when written, it renders on every screen, and it is exactly the string everybody has stopped reading. Ubiquity is what makes staleness invisible, not what protects against it.
- **A figure that needs a note explaining how not to read it is a figure whose existence to check.** The staff report carried a "doses with no record" column beside a note warning that a gap in the record is not necessarily a failure by whoever was on shift — and an omission is a dose *nobody* recorded, so it carries nobody's name at all. The note would have read as a disclaimer on a column that could not honestly exist. The same shape one step in: "0.0%" against somebody who worked no rounds is a denominator that supports a rate perfectly well and an accusation all the same. **The tell: when a screen needs prose to stop a reader drawing the obvious inference, ask whether the figure belongs there rather than writing better prose.**
- **A string transformation that reads as tidying can destroy the thing being tidied.** `.toLowerCase()` on the field label "What I need help with" produced "what i need help with" — a label written in a resident's own voice, with the one word that is the point of it removed. It is the same move as agreeing a plural at the call site: **a value whose correct rendering depends on where it appears cannot be rendered by whoever happens to be appending it.** "Fall — witnessed" is right in a column and wrong in a sentence, so it carries a name and a phrase rather than a `.toLowerCase()` at each use.
- **A screen that cannot be reached from the navigation is not built, however green the tests are.** Guards run bidirectionally — every route has an entry, every entry has a route. The MAR chart passed 517 tests while being unreachable.
- **A refusal that rests on a figure stops being a refusal the moment the figure moves.** The compliance overview states that there is no overall compliance percentage and never will be. The reason it gave was "N of 5 Key Questions cannot be rated at all, so there is nothing to average" — and N was **zero**: all five were rated, so the screen's stated reason for refusing the figure was false on the day it was written. The hero carried the same defect one size larger, in the largest type on the screen: "0 of 5 — Key Questions unratable **as a result**", a causal claim over four unusable checks that had in fact left every panel ratable, and a zero reading as reassurance in the one position reserved for the opposite. The refusals in this file are standing properties, so their stated reasons have to be standing too — averaging ratings taken over unrelated populations is one, a count that happens to be non-zero today is not. **The tell: if the sentence explaining a refusal contains a number, ask what the sentence says when that number is zero.**
- **A repeated segment in a rendered string is two owners agreeing the same fact.** The pharmacy cycle printed "30mg · 30mg · capsules" and "75 micrograms · 75 micrograms · tablets", because `Medication.form` is *form and strength as the register lists it* and the row put the dose in front of it. Neither half was wrong; the second one did not know the first existed. This is the one-owner rule with a tell attached that does not need the owner to be known in advance: **read the string back and look for a value stated twice.** It found this in a screenshot in under a second, where reading both field definitions would not have — `dose` and `form` are both strings, both plausible on a medication row, and the docblock explaining that `form` already carries the strength is four hundred lines away from the call site.
- **Lowercasing a constant you wrote is safe; lowercasing a value out of a record is not.** The document viewer rendered "a representative dnar form", from `document.title`, which is a title somebody typed into a record. The §8 entry above about `.toLowerCase()` destroying a label was written a phase earlier and did not prevent it — second occurrence, same transformation, different field. The distinguishing question is where the string came from: `SHIFT_NAMES[shift]` and a consent type's `name` are closed vocabularies whose casing is ours to choose, and a document title, an allergy's reaction, a resident's own words are not. A mechanical guard was written and thrown away: 30 sites lowercase into JSX and roughly 27 are legitimate, so it would have needed 27 escape comments and been wallpaper inside a week — the exception-list failure this file already names, arrived at for the third time. **What is enforceable instead is the question, asked at the call site: is this string one we wrote, or one somebody recorded?**
- **Before counting what relies on a record, ask whether two of them are the same fact stored twice.** The document viewer's rail said "3 records rely on this document" for a DNAR that two of the three reached through the same field: a resident's resuscitation decision is held on the resident and mirrored under future plans, and the fixture builds the second from the first. Two readings of one field break together, so the honest count was two. This is a denominator inflated from inside the record rather than from a wrong population — the aggregate rule one level down, where the duplicate is not a duplicate row but a duplicate *route to the same row*. **The tell: when a list of referrers has two entries pointing at the same screen, say whether they would break separately.**
- **The complement of a population is not automatically a gap.** A chart bar read "213 of 306 documents in date", and its hatched segment therefore claimed 93 records "nobody has written" — but an expired document *was* written, by somebody whose name is on it. That is Rule 3 (a recorded negative is not an unrecorded value) appearing in an aggregate rather than in a cell, where it is much harder to see: the cell version is one wrong badge, the aggregate version silently recruits every recorded-but-unwelcome answer into the missing-evidence count and inflates it. The fix was to count the thing that genuinely has an unrecorded state — documents carrying an expiry *decision* — and being out of date went back to being a finding. **Before hatching `total − recorded`, say what the remainder actually contains.**
  It came with the one-owner rule attached: the same population needs **two phrasings**, because "42 consents sought" against a missing count reads as forty-two consents that were sought. The bar says `population`, the missing list says `missingPhrase`, and neither call site agrees the wording itself.
- **A guard blind to a second medium is not a guard, however green it prints.** `check-hatch.mjs` exists because the hatch is the most load-bearing visual in the product and a second, slightly-different copy is the drift that survives review. It read `.css` files, which was the whole world until the Dashboard's charts needed the hatch as an SVG `<pattern>` — a chart area and an arc stroke cannot take a CSS background. The rule was never violated and the mechanism covered nothing: a second `<pattern>` anywhere would have shipped under a tick that said the treatment had exactly one definition. **The tell: when a concept gains a new medium — a new file type, a new renderer, a new output — every check that names that concept is now narrower than its own success message.** The check either learns the medium or its message has to stop claiming the concept. This one learned it, and the message now says *per medium*.
- **A chart can be accurate and unreadable, and the fix is never the axis.** The area chart plots doses recorded against doses due; this home records about 98% of them, so the hatched gap between the two lines is three per cent of the chart's height — drawn exactly to scale, and invisible. The tempting repair is to start the y-axis near the data. **A truncated axis magnifies a gap by hiding zero, which is the reassurance failure run backwards** — alarming rather than soothing, and the same lie about proportion. It belongs with `FLAG_STILL_IN_TIME` above, which manufactured an alarm on every row: a false alarm and a hidden gap cost the same, because both teach the reader to stop looking. **The geometry stays honest and the figure gets printed**, so a day on which six doses went unrecorded says six whether or not six pixels show it. Same move as the aggregate entry above: when a shape cannot carry a fact, the fact is not reshaped, it is stated.
- **A value can be in the DOM and painted over on screen.** An SVG circle with no `fill` declared defaults to black, so the donut arc that took its stroke from the hatch pattern laid a solid black disc across the middle of the chart — over "of 162 doses scheduled today", which is to say over the denominator. Every test passed, and **every test was right**: the string was in the DOM, in the right element, with the right numbers in it. That is the part worth holding on to — this is not a test asserting the wrong thing, which is what most of the entries above are about. It is a test asserting the right thing **about the wrong medium**. A suite that queries text cannot tell a figure from a figure nobody can see, so occlusion, contrast, clipping and z-order are a class no assertion in this build reaches, however well written.
  **So the read-back is a screenshot, not a DOM dump.** The dump was the method while there was no way to rasterise a page; there is one — the Chrome on this machine, `--headless --screenshot`, with `sips` for greyscale, and no dependency added to do it. Every screen carrying a graphic gets looked at, in colour and in greyscale, and the greyscale pass is the one that proves the hatch is doing the work rather than the hue. §3.6's midnight-BST calendar was found the same way and is the same lesson a phase earlier: it was found only by looking at a picture.

- **A value can be correct in the DOM, correct in its class list, and invisible on screen. Only a screenshot finds it. Second occurrence.** The first was the donut: an SVG circle with no `fill` defaulted to black and laid a solid disc over "of 162 doses scheduled today", with every test passing and every test right — the string was in the DOM, in the right element, with the right numbers in it. The second is the staff dashboard's hatched tile, which carried `composes: unrecorded`, rendered `data-state="unrecorded"`, and had a `className` matching `/unrecorded/`. Three assertions, all green, on a tile that painted as a plain white card: a shared `.tile, .tileNow, .tileWarn, .tileGap` rule set `background: var(--bg-surface)` and won on source order. **The second is the worse of the two and it is worth saying why.** In the donut something was drawn over the value; here nothing was wrong anywhere — the class was applied, the cascade simply resolved the other way, and there is no state in the DOM that differs between a tile that hatches and a tile that does not. A `composes:` is a claim about cascade, and cascade has no representation a query can reach. **So asserting the class name is not evidence the treatment rendered**, and the rule that follows is mechanical: a shared shape rule never sets `background` or `border` for a class that composes the hatch — shape in the shared rule, paint per tile.
- **A specific claim built on a false source is more dangerous than the vague statement it replaces, because specificity is what makes it trustworthy.** Signing out destroys everything in memory, so "unsaved changes will be lost" was replaced with a list naming each kind of record and its count — a claim a reader can hold against what is actually there, which is the whole argument for itemising it. The source chosen was the session activity log, whose docblock said every write in the product passes through one logging function. **Nine of the client's nineteen write functions never reach it**: every medication round, PRN dose, controlled drug opening count, review flag closed, care plan draft saved and every undo. A shift's medication records would have been destroyed under a list that never mentioned them — and the reader would have trusted that list *more* than the sentence it replaced, because it was itemised, counted and precise. **Vagueness fails safe; precision does not.** A sentence that says nothing in particular cannot be wrong about medication, and a list that names four things is read as naming all of them. So the question to ask before making a claim more specific is not whether the new claim is better, but **whether the source can carry the weight the specificity puts on it** — and the docblock asserting it could was written when it was true of the two call sites that then existed. `scripts/check-session-losses.mjs` now fails the build when a store in `src/data/access` holds session state and `session-losses.ts` does not ask it, which is enforceable because "holds session state" is a module-level mutable collection and that is a shape a script can see.
- **Testing that a cap is applied and testing that the cap is right are two different tests, and the first passes when the second would fail.** The permission ceiling fixed a whole class at once: each module declares the acts it offers, and a role's level is capped at what the module has. The guard asserted the property — no cell exceeds its module's ceiling — and it is a good guard, and it passes happily on a ceiling declaring that the Dashboard takes writes. **A property test over a derived bound inherits every error in the bound**, silently, because the bound is what the assertion compares against: the test and the defect agree by construction, so there is nothing left to disagree. It took two mutations to know that — remove the cap, and corrupt the cap — and only the second one is about whether the answer is correct rather than whether the machinery ran. This is the Phase 7 proxy entry arriving somewhere new. There it was a hand-written approximation of a rule drifting from the rule; here nothing is approximated and nothing drifts, and the failure is the same shape: **an assertion is only evidence to the extent that its reference could have disagreed with it.** So a property over a table is never the whole guard. The cells that were actually wrong get held by name as well — Dashboard and Reports are Read for everybody, stated outright — because a named case is the one thing a corrupt bound cannot absorb.
- **A permission matrix reads as a specification of somebody else's access, and showing it to its subject is the first time anybody checks it against what they actually do.** Sixteen modules by seven roles is 112 cells, every one plausible on its own, and it was wrong for fifteen phases: a care worker read "Record" against the Dashboard, where nobody writes anything, and a manager read "Approve" against Reports, where there is no work of anybody else's to sign off. Nothing found it, and nothing could — the manager's matrix describes other people, so a reader checks its shape rather than its claims, and a cell about somebody else's job is a cell nobody has the standing to contradict. It was caught the day `/me/permissions` put the same row in front of the person it was about. **The general form: a screen describing a third party is unaudited by construction, and the cheapest audit available is showing it to its subject.** The fix was not to correct the cells — a corrected table drifts the same way — but to declare what each module actually offers, naming the act, and cap every role at it. A guard asserts no cell exceeds its module's ceiling, and `levelFor` throws on a module with no acts declared, because an uncapped module is how "Record" got onto the Dashboard. The same pass found five exceptions naming `/team`, which stopped being a sidebar item in Phase 15: they narrowed nothing for anybody and still read as decisions somebody took.
- **An assertion guarded by a null check is an assertion that can stop running, and the fixtures decide when.** The invitation guard checked that the role and access render above the password fields — inside `if (password !== null)`, because the only invitation in the fixtures expired a month ago and an expired screen has no password fields. It passed by never running. Same shape as the round queue's `rooms.indexOf('—')` returning -1 for ever, arrived at from a different direction: there a copy change killed it, here it was born dead. **The tell is the null check itself**: ask what makes the value null, and whether any fixture makes it non-null. If none does, the branch under it is unasserted no matter how many times the suite is green.

- **A test that identifies a state by the characters it renders dies silently when the copy changes.** The round queue marked an unrecorded room with an em dash, and the guard for "unrecorded rooms sort last" found that row with `rooms.indexOf('—')`. When the dash was replaced with words, the lookup returned -1 for ever and the assertion under it — guarded by `if (unrecorded !== -1)` — simply stopped running. The suite stayed green, the count of tests did not move, and the rule went unprotected. This is the "assertion that cannot fail" entry arrived at from a new direction: the test was not written that way, **an ordinary copy change made it that way**, and nothing in the sweep that caused it had any reason to look at that file. Read a state off an attribute the component sets for the purpose, never off the glyph it happens to print. The same sweep is the reason: a house-style decision moves hundreds of strings at once, and every guard keyed to one of them fails open.

- **`toContain` on a sentence says the value is present, never that it is in the right place.** The late list's claim has to state the *filtered* count and the unfiltered total beside it, and the guard checked `toContain('late in total')` and `toContain(String(total))`. Changing the claim to lead with the unfiltered figure — the Rule 3c defect the guard exists to catch, a count of 26 sitting above a list of 3 — left both assertions true, because the total was still in the sentence; it was simply in the position the filtered count should have occupied. **This is the selector-specificity rule applied to text**: a substring match names a value the way `container.querySelector('ul')` names an element, which is to say not at all. The fix was to read the leading figure and compare it against the pill's own count, so the assertion says *where*.
  The mutation is what exposed it, and one alongside it makes the other half of the point: a second guard survived its mutation because two mechanisms protect the same outcome, and either one alone is enough. That is a guard being belt-and-braces rather than a guard being broken, and the difference is only visible by breaking both. **Neither case is distinguishable from a working guard without running the mutation** — which is the whole argument for running it every time.

- **Two halves of one question, answered to two clocks.** The donut's "due now" read the state baked into the MAR fixture at generation; "not due yet" beside it compared the round's wall-clock time with the home's. Both were defensible on their own and the pair was not: the fixture's instant is when the page loaded and the home's clock keeps going, so a round that opened while somebody had the tab open stayed *not due yet* while the header said otherwise, and one that closed stayed *due*. It read as a chart that would not update. **The tell is not that a figure is stale, because a stale figure looks like a working one; it is that two figures in the same set are computed from different sources.** Where a set of counts partitions one population, one derivation answers all of them or the set does not add up — and it will still add up to the total while being wrong about which bucket things are in, which is why the sum being right proves nothing here.

- **A figure that is correct and indistinguishable from broken is the worst pair on offer, and the fixture is usually why.** "Due now, inside its window" read zero on every load, and it was right every time: the generator recorded *every* round in the past, including one that had opened four minutes earlier, so no dose in the fixture was ever inside its window. The state was unreachable, and no amount of looking at the screen could tell that from a screen that had stopped updating. **A reader cannot distinguish a true zero from a dead one, so an always-zero figure is a defect even while it is accurate.** The check is the standing one about fixtures reaching every branch, and the reason it needs saying again: this branch could not be reached *at any hour*, because the fixture is generated at the moment of the load and the generator finished the round it was standing in. Where a fixture is built against `now`, ask what it makes true of *now* specifically — the states that only exist in progress are the ones it will quietly complete.

- **Spending the alarm vocabulary on something that is not a finding is how the alarm stops working where one is.** The moved-clock notice was built in `--status-caution`, with the amber border and tint a finding wears, and ran to four lines ending "nothing here is a record of what has actually happened today". Every word of that is true of every screen in this build at every hour, because the whole record is fixtures — so saying it loudly *only* where the clock has moved implies the rest is real, and puts a standing alarm on the front door for a thing nobody needs to act on. **A notice is not a finding, and the treatments are not interchangeable.** What a reader needed was the instant, why, and the way back, which is one quiet line. The tell is the same one as the figure that needs a note explaining how not to read it: if the prose is doing the work, ask whether the treatment is wrong rather than writing better prose.

- **A test can be satisfied by the wreckage of the act it tests.** The group overview's switch calls `setActiveSite` then `navigate('/')`, and its test asserted the overview was *still on screen* afterwards. It passed — because the memory router had no `/`, so react-router resolved against an undefined match and threw, and nothing moved. Had the button worked, the overview would have unmounted and the assertion would have failed. **This is worse than a vacuous test**: a vacuous test asserts nothing, and this one asserted the failure, so the defect and the green tick were the same state. Nothing could distinguish them from inside the suite; the unhandled rejection was the only trace, and it was in a file whose 16 assertions all passed. **The tell: an assertion that the thing under test is still present after an action whose whole purpose is to remove it.** If clicking is meant to navigate away, `expect(thing).toBeTruthy()` afterwards is a test of the crash. Assert both halves of the act — where the reader landed, and what the session did — and mutate each half separately, because one mutation would have passed on the other's assertion.
- **A slow test may be measuring a slow screen, which is the useful case.** `zonedWallClock` constructed a new `Intl.DateTimeFormat` on every call, and `withoutNoteToday` called it once per note — 11,125 constructions, 405ms. It surfaced as a 42-second test file, and the tempting reading was "tests are slow". It was never only a test cost: `zonedDate` is called in loops by the dashboard, the group figures, the MAR chart and the note series, so **real screens were blocking the main thread for 400ms on every load**. Construction is the expensive part of `Intl` — about 36µs against well under a microsecond to format with one that exists — so the fix was a cache keyed by shape and zone, not a smaller loop. **This is the argument against raising a timeout: the clock was the instrument, and reading it found a product defect.** A timeout raised three times had already hidden this once. Before raising one, ask what the number is telling you about the screen, and profile rather than guess — the same run also disproved two confident hypotheses (unpaginated rendering, simulated latency) that would each have sent the fix somewhere useless.
- **A flag typed once at a terminal is invisible to everyone who clones afterwards.** `--legacy-peer-deps` made this tree install for weeks and left nothing behind — no `.npmrc`, project or user. The first machine to run a plain `npm install` was a build server, which is where the ERESOLVE finally surfaced, long after the decision that caused it. Same family as an over-broad gitignore: **the state that matters lives somewhere nobody reading the repo can see.** A shell history is not a decision the project has made. If a command needs a flag, the flag belongs in a committed file — or the need for it does, as an `overrides` block that says which peer range is being disregarded and why.

- **A test's history is what tells you whether an edit is a fix or a retreat.** The care plan queue's completeness guard failed when paging landed, and it could have been made green in one line. What stopped that was a comment in the test recording that it had *already* been hardened once, after asserting `rows.length % 10 === 0` — true of ten, of twenty, and of an empty list. Editing the same guard a second time, in the same direction, is a pattern; editing it once looks like maintenance. **Neither the assertion nor the diff carries that information — only the note left behind by the last person did.** So when a guard fails and the tempting fix is to adjust what it asserts, read its history first, and leave the reason behind when you change one. The check that survives is the one whose author explained why it was tightened.
- **A red test can stop matching rather than fail, and that is the harder one to notice.** The same guard counted rendered rows against `residents × domains`. Paging did not break the property it protected — the constant was still the source, the denominator was still right — it broke the *proxy*, and the test went red for a reason that had nothing to do with the defect it existed to catch. A test that fails on a real regression invites you to fix the code; a test that has merely stopped matching invites you to adjust the number until it is green, which is the same keystroke and the opposite act. **The tell: ask whether the thing under test actually changed, or only the way the test reaches it.** Counting rows was always a proxy for "the constant is the source"; asserting the denominator through the claim the screen makes is the thing itself, and survives any change to how rows are drawn.

- **jsdom performs no layout, so no assertion in the suite can see a screen clip.** Every `getBoundingClientRect` there returns zero, which means a clipping test written as a vitest test passes on any grid at any width — not a weak check, a check that cannot fail. **This is the third variant of one family**, and the three together say the thing better than any of them alone: the donut's black disc drew *over* a value that was correctly in the DOM; the hatched tile applied a class that the cascade then overrode, so nothing in the DOM differed between hatching and not hatching; and this is a check that cannot perceive its own subject. Right assertion, wrong medium, three times. What it cost when nobody was looking: the MAR week captioned "Week of 31/08 to 06/09" and rendered six days, and the Reports panel — whose entire subject is denominators — rendered "15 of", "0 of", "8 o", every one guillotined, with the bars squeezed to nought pixels so the hatch was not drawn at all. 517 green tests, a screenshot to find it. **A real browser is not a nicety for anything geometric; it is the only instrument that reads that medium**, which is why `check:layout` is in `verify` rather than beside it.
- **A guard that names one subject is measuring that subject, not the rule.** `check-week-fits.mjs` — now folded into `scripts/check-layout.mjs` — asserted the week on `res-okafor` and printed a tick meaning "the week fits". The grid's width is data-dependent — seven days times however many rounds a day that resident is on — so `res-okafor` at three rounds fits in 1,194px and the five residents on four rounds need 1,454px. The fix had been validated against the one resident it was written for, reported as done, and was wrong for 5 of 28. It is the specificity rule pointed at the *subject* rather than the selector, and the repair is the same one this file reaches for everywhere else: **the guard counts, and states the count against its denominator** — "23 of 28 weeks fit" — because a number that falls is a regression somebody can see, where a tick is a tick either way. The same pass caught the success message doing it too: it still read "and the week fits", which is a claim wider than the check underneath it, and that is exactly how a guard starts reading as coverage it does not have.
- **A mutation whose build fails silently is not a mutation, and it reports the previous mutation's findings.** Commenting out a hook call to break a guard left the import unused, `tsc -b` failed, `npm run build >/dev/null 2>&1` swallowed it, and the check ran against the *last successful* dist — so the run printed a failure, the failure looked plausible, and it was the previous mutation's. **A mutation that fails for the wrong reason is worse than one that passes**, because a pass prompts investigation and a failure is what you were hoping for. It is the reassuring-branch problem wearing a red tick. Two things follow, both cheap: **never hide the build output of a mutation run**, and **read which finding came back, not just the exit code** — an identical failure across two different mutations is the tell, and it is only visible if the findings are printed rather than counted.

- **A denominator can be destroyed by CSS.** Rule 4 is written as a rule about strings — no bare counts, use the `Aggregate` type — and every mechanism enforcing it works on strings. None of them can see `white-space: nowrap` on the pill that holds "of 40 on record at Rosewood Court", which set the grid track's floor above what the content column has at 1280 and pushed the last dashboard tile off the screen with its denominator cut mid-word. The count rendered; the reader saw a number with nothing under it, which is the precise thing the rule exists to prevent. Same defect, same afternoon, on the Reports panel and in a table cell. **The tell is that a fix which reads as typography — nowrap, a fixed track, a `16rem` label column — is a width decision, and width decisions are where denominators go to die.**

- **Every line you read can be true and the run still red — you read the wrong part of the output.** `npm run verify > log 2>&1; echo $?; tail -6 log` reported success twice over, and both reports were accurate. The status was `tail`'s, because a compound command exits with its *last* element rather than its worst. And the six lines were the layout guard's ✓, which sits at the foot of the chain and passes independently of the tests above it — so a run with `27 failed | 1209 passed` printed a tick as its final word. Nothing lied. **This is not a wrong assertion; it is a correct reading of the wrong frame**, which is the same family as the donut's black disc and the hatched tile that painted white — right assertion, wrong medium — arriving in a terminal rather than on a screen. The tell is specific and checkable: **the tests ran, and their result was never in the frame.** So a chain's tail is not its verdict. Read the summary line of every stage that can fail, or make the runner print one, and never take an exit code from a pipeline whose last command is a reader.

- **A fix that works, followed by another defect of the same kind, is a fix to a symptom.** The Figma exporter resolved the layout away — `getComputedStyle` and `getBoundingClientRect` turning flex, gap and grid into one absolutely-positioned `<div>` per box — on the reasoning that a plugin handed finished pixels has nothing left to misinterpret. The plugin wanted the opposite: it builds auto-layout *from* flex and gap and reads type from elements in normal flow, so the two things it needed were the two things being stripped. What followed was six rounds of repair — ExtraLight fonts, per-weight family names, 500 and 800 rounded, a donut a quarter turn out, a capture width frozen into the file, a scaling wrapper bolted on to undo it — and **every one of them was a real defect, correctly diagnosed and correctly fixed.** That is what made the premise invisible: a wrong premise does not announce itself as one wrong thing, it announces itself as a queue of right ones. The tell was there from the second round and went unread. **Count the repairs, not their difficulty**: three consecutive fixes in one area, each of which worked, is the signal to ask what they have in common rather than to reach for the fourth. Here the answer was that all six were reconstructing information the first decision had thrown away.

- **A file can lie about its own identity, and nothing in the code, the styling or the rendering will show it.** `@fontsource/manrope@5.3.0` ships woff2 whose name table reads `Manrope ExtraLight SemiBold`, `Manrope ExtraLight Medium`, and so on. The outlines and `usWeightClass` are correct, so the screen renders correctly and a probe string measures five distinct monotonic widths — and every tool that reads a font's *name* rather than its outlines reported the whole product as ExtraLight. Six rounds of repair went past it, because every one of them examined something that was working: the CSS was right, the weights were right, the rendering was right. **The artefact was wrong about itself, and no amount of reading the source that referenced it could reveal that.** The tell, when it finally came, was **two formats of the same font disagreeing** — the `.woff` files of those same weights are named correctly, which is why an earlier check of the `.woff` cleared them while the browser was loading the `.woff2`. It was found by decompressing the binary and reading the name table, and it could not have been found any other way. **So when every layer you can read is correct and the symptom persists, stop reading the layers and go and read the artefact.** Checking the input is not checking the output either: subsetters rewrite name tables, so the verification belongs on the file that ships. And it was inherited rather than invented — Google's `Manrope[wght].ttf` declares family `Manrope ExtraLight` because a variable font's name IDs 1 and 2 describe its default instance, and Manrope's default is wght 200 — which is the same lesson one level up: **a dependency's defect is usually its dependency's defect, and the fix belongs where the name is set, not where it is copied.**

- **A legend is drawn in the medium of the thing it explains, not the medium of the boxes around it.** The dashboard's chart legend composed the CSS hatch while the bars beside it filled with the SVG `<pattern>`: two definitions of one treatment, agreeing nowhere. At twelve pixels the gradient lays down most of one band of a pale tint inside a dashed border, so the swatch rendered blank — a key whose "not recorded" entry had no treatment in it, next to a chart where the same state is unmistakable. **It generalises past the hatch.** Any swatch, chip or indicator that explains a visual property has to be produced the same way the property is: a legend for a dashed stroke drawn as a CSS border, a legend for an SVG gradient drawn as a flat fill, a legend for an opacity drawn at full strength. The two will agree at the size they were designed at and diverge everywhere else, and the legend is the one place a reader goes *because* they could not tell — so it fails exactly where it is being relied on. The rule is a question at the call site: **what draws the real thing, and is this drawn by that?** The sweep it implies is cheap and worth doing per medium rather than per component: this build had the split in one place, because the dashboard is the only screen with an SVG hatch, and Reports and Compliance draw bars and swatches both in CSS and were already consistent.
- **Converting a layout moves which declarations are doing the work, and a property nobody edited changes meaning. Second occurrence.** `.tile` carried `height: 100%`, inert under grid where the track stretched the item regardless. Under flex it became decisive in the opposite direction: `align-items: stretch` **exempts an item that already has a definite cross size**, so every tile sized to its own content and four screens rendered ragged rows — a tile holding a hatched block standing taller than three holding a numeral, which in a row that is one comparison reads as a difference in the data. Nothing about that line changed; the container underneath it did. The first occurrence was `--tile-chrome` in the same file a week earlier: `flex-basis: 0` is clamped by `box-sizing: border-box` to padding plus border, where a grid track has no such floor because padding sits *inside* it. Both are the same shape — **a declaration whose behaviour is defined by the layout mode it sits in, silently re-scoped by a conversion.** So a grid-to-flex conversion is not only a change to the container: **every declaration on the children has to be re-read in the new mode**, and `height`, `min-width`, `flex-basis`, `align-self` and percentage sizes are where the meaning moves. Carry it into the remaining conversions as a thing to look for rather than a thing to discover — the tell is that the diff looks like one line on a container and the regression appears on a child that the diff never touched.

- **Where one concept has two implementations, the difference between them is usually the load-bearing part, and a swap is what destroys it.** The unrecorded hatch exists twice on purpose: the CSS gradient bands `--status-unrecorded-tint`, and the SVG pattern bands `--status-unrecorded`. That is not drift — `charts.tsx` records the reason, which is that **at ten pixels of bar the tint is white, and a hatch nobody can see is a solid neutral fill**, the one thing Rule 2 says the treatment must never become. So when the Figma importer turned out to drop SVG patterns and keep CSS gradients, "just use the CSS one in the charts" looked free and was not: the bar gaps are 7–20px tall, and the swap would have reproduced, on screen, the exact defect the SVG pattern was introduced to prevent — in the direction that hides a gap rather than inventing one. **The tell is that a second implementation of one concept is either drift or a decision, and you cannot tell which without reading why it exists.** If there is no recorded reason, it is drift and should be collapsed; if there is one, the reason names the property a swap will cost. Two further things this run showed. **A guard can block the obvious repair, and that is the guard working**: `check-hatch` forbids a second `repeating-linear-gradient`, so the tempting fix — a stronger gradient for the charts — cannot be made quietly, and the cost has to be argued instead. And **the cheaper experiment comes first**: a one-attribute test that might recover everything was pending while a 115-line chart rewrite recovering two thirds was being scoped, and building in that order would have paid the whole cost before learning it was unnecessary.

- **An observation is evidence for what it observed, not for the claim it happens to sit beside.** An import was taken while the dashboard was on flex, and it showed the layout arriving correctly. That fact was then used to justify reverting flex to grid — because the *hatch* failure had been shown not to be caused by grid, and "grid did not cause the hatch failure" was carried across to "grid is fine for layout". It was not: the importer builds auto-layout from flex and gap, grid has no equivalent, and the arrangement broke. **The evidence for "grid is fine" was an import of a version that had no grid in it.** The tell is cheap and mechanical: when citing an observation, name the version it was taken on and check that the claim you are making is about that version. Here the two differed by the single declaration under discussion.
- **A number that decides an accessibility question cannot come from memory, and the direction it errs in is not random.** Two contrast ratios were written into a decision record before being computed — 1.11:1 and 2.91:1 — and both were wrong. The real figures are **1.12:1 and 3.43:1**, and the second one crosses WCAG 1.4.11's 3:1 floor for non-text contrast, which the guessed figure did not. So both errors ran the same way: they made the two hatches look comparably weak, and a swap from one to the other look like a matter of degree rather than a matter of a rule. **Wrong numbers do not scatter; they land where the argument was already leaning.** Compute the figure, paste the computation, and be most suspicious of an estimate that happens to support the change you were about to make.
- **A guard that fires on its own documentation teaches people to word around it.** `check-hatch` matched `repeating-linear-gradient` anywhere in a line, so a docblock *explaining* why the hatch has one owner counted as a second declaration of it. The pressure that creates is the wrong way round: the cheapest fix is to reword the comment, and the habit that builds is writing about the rule obliquely — which is exactly how the next real copy gets in under a comment. A guard should match the construct, not the word for it: declarations for CSS, and prose lines skipped outright.

- **A screen's meaning can change because a constant changed, with nothing on the screen edited.** The invitation lifetime went from seven days to 72 hours, set in `invitations.ts` so both products read one rule. On the Team screen, "never given access, and never set up" had always described an open invitation and an expired one in the same words. At seven days most unaccepted invitations were open, so the copy was adequate. At 72 hours most have expired, so the same copy became misleading most of the time. The dashboard banner changed the same way: "3 invitations nobody has accepted" listed three people, all expired. **Nothing in the diff touched either screen, and no test could have caught it**: both screens still said exactly what they always said, and every test of them still passed, because what moved was how often the state they fail to distinguish occurs. It was found by looking at the screens with the new fixtures, after the suite was green. **The tell: when a constant decides how often a state occurs (a lifetime, a threshold, a window), find every screen that renders that state and ask whether its copy still holds when the state is the common case rather than the rare one.** A rarity a screen was quietly relying on is part of its meaning, and it lives in a file the screen does not import.

## 9. Stop and ask

Ask before doing anything expensive to reverse. Frank is a product manager, not a developer — a wrong assumption costs him a rebuild, not a quick undo. Stop and ask before:

- Installing any dependency not already in `package.json`.
- Adding, renaming or removing a design token, or introducing a colour or type step.
- Changing the shape of a fixture type, especially a status union.
- Restructuring folders, routing, or the app shell.
- Changing anything in `FRONTEND_PRD.md`.
- **This file is the exception, and only for §8.** Standing checks are written here in place as they are found, because Frank's local copy does not carry them — handing one over would delete every check written since Phase 3, in the file that exists to prevent exactly that. New §8 entries are added and then reported. Wording for every other section comes from Frank.
- Deleting or rewriting existing working code to accommodate new code.
- Any workaround that would relax a rule in this file "temporarily".

When something in the spec is ambiguous or looks wrong, say so and wait. Do not pick the interpretation that is easiest to build.

## 10. Working cadence

- Build **one phase at a time**, in the order in `FRONTEND_PRD.md` §8. Stop at the end of each phase for review.
- In Phase 1, stop after **each screen**. From Phase 2, a full module per review is fine unless problems appear.
- Before starting a phase, restate what you are about to build and wait for approval.
- **Reports in chat are short**: what to look at, and anything needing a decision. Nothing else.
- **Bugs, reasoning, decisions, and anything discovered go in `PROGRESS.md`** — never in the chat reply. Append, do not rewrite history.
- Every screen is reviewed against all seven states before it is called done: Loading · Empty · Partial · Populated · Stale · Error · Read-only.

- **Settable if and only if it is read at render is necessary, and it is not sufficient.** The settings screen has enforced the first half since Phase 15: a figure baked into fixture generation cannot be offered as a control, because the records were produced against the old value and the control would move a label and not a single dose. Deactivating a risk assessment template passes that test — the screens iterate the template list while they draw — and it is still not safe, because `RiskStatus` has two members and `not_assessed` would silently acquire a second meaning: nobody has done this, or this home does not do this. **A setting that changes what an existing state means needs a second rendering rule, or a union member quietly becomes two facts.** That is the Evidence Invariant arriving inside a type rather than on a screen, which is the one place this build had never had to look for it. The rule that follows is a question to ask of any new setting: not only "is this read while the screen draws", but "does turning this off change what a record already in the database is saying". Where it does, the setting is held on the thing being configured and the screen renders the pair — a completed assessment against a deactivated template keeps its record, quietly, with its author and date; a never-assessed one against a deactivated template renders plain rather than hatched, because hatching would claim a gap the home has decided is not one. And both directions move a denominator for a reason that is not care, so the control states what it will do to the figure before it is thrown.

- **A guard that reports what it did rather than what it reached cannot tell you it reached less.** `check-selector-specificity.mjs` blanked comments with a regex, and `authority.test.tsx` contains `path !== '/*'`, excluding the router's catch-all route. The regex cannot tell a comment from a string containing one: it paired that `/*` with a block-comment terminator ninety-three lines later and blanked everything between, including **four of the queries the check exists to read**. It then printed "every query is scoped, named, or identified" over a file it had read a third of. Nothing was disabled, nothing was excused, and the count of deliberate opt-outs was accurate. **The tell was two verdicts on an identical line**: the same `container.querySelector('nav')` passed in the morning and failed in the afternoon, because a docblock moved and the hole moved with it. Nothing about that line changed, and had the edit gone the other way the hole would still be there. A guard whose blind spot drifts with unrelated edits is worse than one with a fixed blind spot, because it looks like flakiness and gets retried rather than read.
  **This is the layout crawl from another angle, and the two belong to the same family.** That one signed in as whoever the form prefilled, so when the rail started filtering by role it stopped reaching Compliance, Reports and Settings — and reported the same "70 screens crawled" as before, because the crawl caps at 70 and was already hitting the cap. Both guards reported their *activity* faithfully. Neither could report its *coverage*, and coverage is the only thing a guard's success message is about. The shape is: **a check that can silently skip part of its input, and a success line phrased over the whole of it.**
  So the rule is a question to ask of every guard, including the ones in this list: **if this check silently read half of what it was pointed at, would its output look any different?** If the answer is no, the fix is one of two things and never better wording. Either the check is made unable to skip — `scripts/lib/strip-comments.mjs` is a scanner that knows a string from a comment and throws if it ever changes the length of its input, because every guard using it maps findings back to line numbers — or it states what it reached against what it was given, the way `check-layout.mjs` now names the role it crawled as and fails outright if that role's rail is missing Settings. **A tick is a tick either way; a number that can fall is a regression somebody can see.**
  One corollary, because it cost a second scanner: **a stripper for one medium is not a stripper for another.** The JavaScript scanner treats `/` after `(` as the start of a regex literal, which is exactly the shape of `url(/assets/x.svg)`, so pointing it at CSS would eat declarations. `check-tokens.mjs` had inherited the same regex and got its own scanner rather than a shared one with a flag.

- **A test that asserts a refusal is printed does not assert the refusal.** The tell is mechanical: *would this test pass if the refused thing were added beside the sentence?* Three screens in this build state a refusal in the largest type on them — "there are no counts of your work on this screen, and there will not be", "there is no overall compliance figure and there will not be", and the staff profile's statement that it is not a performance record — and each one is a promise that a figure is absent. A test matching the sentence proves the promise is on screen and says nothing about whether it is kept. Note immutability is the shape to copy: it asserts the sentence **and** that no edit control is in the document, so the rule and its evidence are the same assertion.
  Two of the three refusals in this build were already held properly when this was written — compliance strips the panels and asserts no `%` survives; the staff profile asserts no `[data-numeric]` is on the page — and only `/me`'s was sentence-deep. How that was established is the next entry.

- **A new guard is mutated before it is trusted, and the reason is not that guards are often wrong.** `check-assignment-reach.mjs` shipped with a dead-entry check reading `!findings.length && false` — a condition that cannot be true, so no dead entry could ever be reported and the count printed in its success line was always zero. It was written in the same hour as the entry above about assertions that cannot fail, by somebody who had just written that entry. **That is the second time in this build that an entry failed to inoculate its own author** — the first was the Dashboard's date-kind guard asserting that *at least one* row rendered a date while every review on the screen was widened, written minutes after the specificity entry by the person who wrote it.
  Two occurrences say the rule is not "remember the entry". Familiarity is not the defence and never has been; the entries are long and the build is longer, and the moment of writing a guard is the moment the author is most certain and least able to see it. **The defence is the mutation, run against the new guard before it is believed.** Breaking the code a guard was written for takes a minute and answers a question reading cannot: the same pass that found `!findings.length && false` also found that the guard could not see its own writer, because `includes('residentAssignment')` is false for `setResidentAssignment` — so the one screen that writes the field did not register as touching it at all. Neither defect is visible in a green run, and both are obvious the moment something is deliberately broken.

- **Auditing whether a check exists is not auditing what it checks, and this shape is not caught by knowing about it.** An audit of which constraints in this build were held by nothing reported three refusals as defective. Two were not: compliance strips every panel from the page and asserts no `%` survives, and the staff profile asserts no `[data-numeric]` is anywhere on it. **The audit had searched for each refusal's wording, found that a test mentioned it, and stopped** — activity rather than coverage, in an audit whose entire subject was that distinction, written one entry below where the distinction is recorded.
  **Third occurrence, and the third time it arrived inside the mechanism built to catch it.** The layout crawl reported seventy screens while reaching a smaller product. The selector guard printed a tick over a third of a file. This one is an audit for that defect, committing it. The pattern across all three is not carelessness and not ignorance: in each case the author knew the rule, had just written it down, and was looking at the output rather than at what produced it. **That is the whole difficulty — the moment of checking and the moment of being satisfied are the same moment, and knowing the failure mode does not separate them.**
  So the rule is procedural rather than mnemonic, and it is the same one the mutation entry arrives at from the other side: **an audit's finding is a claim about a test, so read the assertion or break the code under it.** A test's name, its subject, and the fact that it mentions the thing are all evidence that somebody intended to check it, which is a different fact from whether it does. A search over wording finds intent every time and coverage never.
- **An approximation's failure direction has to be demonstrated, not reasoned about.** The percentage guard needed a scope for "the denominator is beside it", and the scope chosen was the enclosing component, with an argument attached: it can only be wrong by flagging a percentage whose denominator lives further away, which is a false alarm somebody investigates, and it cannot pass a bare one, because a bare one has no denominator in any scope. The argument is clean and it is wrong. **A bare `{92}%` added to `DashboardRoute` passed**, because that component is six hundred lines long and contains an unrelated `of {` somewhere inside it — a pass for the wrong reason, which is exactly what whole-file scope had already been rejected for, at a smaller scale. The reasoning had quietly assumed a component is small.
  The fix was a twelve-line window as well as a component, and **how twelve was arrived at is the part to copy**: the widest compliant case in the build is five lines, plus room for a comment between them. A threshold picked from the data it has to admit, with the losing direction named — tightening it produces false alarms and never silence.
  The general rule: **a claim about which way a proxy fails is a claim about behaviour, so it is established by breaking it, not by thinking about it.** Both halves need a mutation: one that should fire, and one that should not. The argument for a safe direction is the most persuasive thing available at the moment of writing a guard, and persuasiveness is not the property being claimed.

- **A mutation that silently does not mutate is indistinguishable from a guard that catches nothing.** Checking the percentage guard meant adding a bare percentage to a screen that had none, and the edit replaced a string that is not in that file. Nothing was injected, the guard printed its tick, and the tick was read as the guard passing a case it had never been shown. The tell is the shape of the output: **a mutation that changed nothing and a guard that caught nothing produce the same line.**
  This is the entry about a mutation whose build fails silently, arriving one level up — there the build broke and the previous `dist` was checked; here the edit broke and the previous source was checked. Same structure, same reassuring result, and the same fix: **confirm the mutation landed before reading the verdict.** One `grep -c` on the injected string costs a second and converts a silent pass into a visible zero. It matters most in exactly this situation, which is a tool being used to check the tools: nothing else in the run is watching, and the thing under test is the only thing that would have complained.

- **A guard can be entirely correct about its property and blind to the one that mattered, and the tell is that it passed.** `check-layout.mjs` asks whether anything is lost at 1280px: clipped text, a value pushed off the content column, a bar squeezed to nothing. Phase 19's verification card rendered at the full 1440 — `.card` sets a surface and never a width, and the sign-in screen constrains itself through a two-column panel that the new screen did not use — and **the guard passed it, correctly**. A card at full width loses nothing. It is a form whose fields run the width of a monitor, which is a different defect: not a value a reader cannot see, a layout a reader cannot use.
  So a screen can be wrong in a way no existing guard is even about, and no amount of strengthening the clipping check would reach it. **The failure is not in the guard, it is in believing a passing guard is a statement about the screen rather than about its own question.** The instrument that found it is the one §8 already names for the donut and the hatched tile: look at the picture. What is new here is that the previous two were caught by a *missing* check and this one was not missing anything — the check ran, answered its question correctly, and the screen was still wrong. **A green guard tells you what it asked, never what it saw.**

- **A guard that fails as an uninformative timeout costs the next person the diagnosis, which is most of the value of failing.** The same layout crawl broke when verification landed between sign-in and the product: it clicked submit and waited fifteen seconds for a `<main>` that was two screens away, then failed with `page.waitForSelector: Timeout 15000ms exceeded — waiting for locator('main')`. Every word true, and it names the symptom of a step it does not know exists. The reader is told where the crawl gave up and nothing about what changed.
  A guard's failure message is read by somebody who does not yet know what broke — that is the situation it exists for — so **a message naming only what it was waiting for has done the cheap half of the job.** The fix is not longer prose: it is that a step which can fail names itself, so the failure says "signed in, and the verification screen did not appear" rather than "no main". The same reasoning as the layout guard printing *23 of 28 weeks fit* rather than a tick — a number that can fall is a regression somebody can see, and a named step that did not happen is a diagnosis somebody does not have to repeat.
  **Caught before it failed, for the first time.** Offering the organisation setup after verification put a third screen between sign-in and `<main>`, and the crawl signs in as the registered manager, the one role that sees it. The failure was predicted from this entry while the step was being designed, so the crawl learned the step in the same change: it waits for the offer and fails saying the offer did not appear, then takes "Go to the dashboard" and fails saying the dashboard did not appear. **An entry that only explains a failure after it happens is a note; this one changed a design before the failure existed**, which is the only direction in which a standing check saves the diagnosis rather than recording it.

- **A field arrives with its writer or it does not arrive.** Phase 20 was asked whether to add the family-message field to `ManagerReview` and leave its control for Phase 21. The answer is no, and the reason is not tidiness. Every clinical field in this build is a closed union with an unrecorded member, and the unrecorded member renders hatched — so a field nothing writes puts a **gap** on the screen: the product saying a record is missing something, with no control anywhere to complete it. A gap invites completion. An absence does not. Adding the field early converts "this product does not hold that" into "this record is incomplete", which is the one distinction §1 exists to protect, inverted by an act of scheduling.
  The second half is that it buys nothing. The type, the fixture builder and the form all have to be touched whenever the field lands; adding part of it early splits the work and leaves a dead branch in between — a state no fixture reaches, which is the standing check about a branch nothing renders. **The test is not "is the field ready" but "is there a control that writes it". If there is not, the slot stays empty rather than half-wired**, and empty means absent rather than a blank waiting to be filled.

- **A cast that silences a check is the rule obeyed in letter while the thing it protects walks through another door.** §6 forbids `any` and requires a comment naming what removes a `@ts-expect-error`. Neither was violated by the Phase 20 review form, which built its patch as an object literal cast `as Partial<ManagerReview>` — and the cast compiled over a real mismatch, that `recordedAt` is an `IsoDateTime` template type and a bare `toISOString()` is a `string`. The rule was kept and the protection was gone.
  **Word it as the class, because the next one will not be a `Partial` either.** Anything that makes the compiler stop asking is the same move: `as unknown as T`, a non-null `!` on a value that can genuinely be absent, a widened parameter type, an index signature that accepts every key, a `satisfies` swapped for an `as`. The question is not which syntax was used but **whether a check that would have run did not**. Where the answer is yes, the fix is almost always to build the value at its real type and then place it — the literal was cast because it was being keyed dynamically, and constructing it typed first and keying it after costs one line and restores the check.
  The tell is available without reading types: **a cast next to a value being constructed, rather than at a boundary where data arrives.** A cast at the edge of the product — a route parameter, a parsed fixture, a `JSON.parse` — is asserting something about the outside world that cannot be checked. A cast in the middle, on something this code just built, is asserting something about code the compiler can see, which means the compiler disagreed and lost.

- **A stub is honest when believing it costs nothing, and dangerous when believing it substitutes for an act somebody would otherwise perform.** This build is full of the first kind: the MAR export, the inspection pack, the data export, prescribing. Each says what it would produce and produces nothing, and a reader who believes it worked is out a file. Nothing in the world was supposed to happen and nothing did.
  The family notifications are the second kind and they are the only ones in the build. "Shared with family" does not share anything, and a manager who reads it as *the family were told* **may not telephone them** — and for an incident that is a family not hearing that their relative fell. The screen did not cause the harm; it occupied the place where an action would have been decided on, and the reader moved past it satisfied.
  **The test is not "does the screen say it did not happen".** Every stub here says so. It is: **would somebody skip a real-world action because they think this one happened?** Where the answer is yes, three things follow that are not required of the first kind. The statement cannot sit behind a click, because the risk is precisely somebody not clicking — that is the opposite of the sign-in screen, where the recovery link was the right place for it. It must read as an instruction rather than a caveat: *nobody has been told; if this family needs to know today, telephone them.* And no status may imply an act in flight — an invitation that says "Invited" implies an email travelling and a status that will turn Active, and here nothing was sent and nothing can activate, so the state says what it is: a decision recorded, with nothing sent.

- **"Settable if and only if read at render" is the wrong axis, and the right one is what kind of claim the setting is.** A setting is either **a claim about the future** — what happens to records made from now on — or **a term in a claim the record already makes**. Only the second needs a second rendering rule, and that is why the four-state treatment does not spread by symmetry to every toggle on the screen.
  Review frequency is the first kind. A completed review carries the date it falls due next, computed when it was completed; changing the interval changes what the *next* one buys and moves nothing already written. Nothing needs a second rendering, and the card's sentence — "applies to reviews completed from now on, dates already in the record do not move" — is the whole of it.
  A risk template's activation is the second kind. `RiskStatus` has two members, and deactivating a template makes `not_assessed` mean either *nobody has done this* or *this home does not do this*: **the setting reaches back and changes what a record already on file is saying.** So the state is held on the template, the screen renders the pair, and the four combinations are spelled out — a completed assessment on a deactivated template keeps its record quietly, an unassessed one renders plain rather than hatched, because hatching claims a gap the home has decided is not one.
  **The question to ask of any new setting is therefore not "is this read while the screen draws".** It is: *does a record already in the database say something different after this changes?* Where the answer is no, it is a control and a sentence. Where the answer is yes, the setting is held beside the thing it configures rather than inside it, and every state of the pair is written out before the toggle ships.
  Two corollaries, both of which cost something in this phase. **A setting whose change would reach back but cannot be rendered honestly is refused rather than engineered around**: round times are baked into every MAR record, and a pending change with an effective date is a scheduling feature in a build with no scheduler — a promise nobody keeps, which is a control that does nothing in a more convincing costume. And **a setting that would silently invalidate existing records is worse than a dead control**: a Family Portal switch that made fourteen recorded consents unusable is not a configuration option, it is a way to break a record from a screen that looks like preferences.

- **The question a check asks can itself be about the wrong thing, and nothing in the answer reveals it.** Every deploy from Phase 17 to Phase 22 was verified by fetching the live bundle and grepping it for a string only that phase introduced. The method is sound, the greps were correct, and each one reported honestly that the work was not live — for six phases, while all six were live. The URL was `digi-care.vercel.app`, a stale deployment; the product is served from `digi-care-zeta.vercel.app`. **The subject of the check was never verified once**, because it had been taken from a `vercel.json` rewrite rather than from the person who opens the site every day.
  This is not the guard that reads less than it claims — that one's *scope* is wrong and its output is still about the right artefact. Here every run was right about the artefact it was handed, and the artefact was somebody else's. **A check has two halves, the question and its subject, and only the first is usually written down.** The failure is invisible by construction: a correct answer about the wrong subject looks exactly like a correct answer.
  The defence is cheap and it is not more rigour. **Confirm the subject with whoever would know, once, in words** — a URL, a database, an environment, a branch. Where that is not possible, make the check prove its subject before trusting its verdict: a deploy check that greps for a string from the *previous* phase as well should find it, and a run where neither string appears is telling you about the wrong bundle rather than about the work.

- **A grep over a truncated download answers correctly about a file that is not the file.** Checking which phases were live fetched a 1.3 MB bundle four times, once per string, and three matched while one reported zero. The fourth fetch had been cut short. Nothing in the output could say so: `grep -c` counts what it is given, and what it was given was a shorter file. The same bundle downloaded once and checked locally matched all four, and the local size and the served `content-length` agreed exactly, which is what settled it.
  It is the strip-comments regex arriving over a network instead of a parser: **the check was honest, the input was short, and the output had no way to mention it.** The cheap defence is the same shape as verifying a mutation landed — fetch once, check the size against `content-length`, then ask every question of the local copy. Re-fetching per question multiplies the chance of a partial read and hides it behind an answer that looks like a finding.

- **Never write down that a check passed before it has.** Phase 23's organisation-name guard was mutated to prove it could fail, and it did not: it typed the fixture's own name, so it was true before the wizard did anything. That half is the vacuous-test family and is covered above. **The new half is that `PROGRESS.md` already said the mutation had been caught** — written in the same edit as the test, from the intention, before the mutation was run. Had the mutation never been run at all, nothing would ever have contradicted it: the note was specific, plausible, and about a check the build does contain.
  Every other entry in this family is a guard reporting the wrong thing, and a guard can be re-run. **A record written ahead of the act it records is worse, because a note cannot be re-earned**: once it is in the history it reads exactly like the notes around it that were written after the fact, and the next reader has no way to tell which kind it is. It is the stub that substitutes for an act, turned on the build's own evidence — a sentence occupying the place where a verification would have been, so that the verification stops looking necessary.
  So the order is mechanical and the entry is the rule: **run the check, read its output, then write the sentence** — and the sentence quotes what came back ("the same mutation, confirmed landed, now fails `names the organisation where every screen reads it`"), because a note that names the failing test was written after one existed.

- **A screen describing what it can do is a claim, and a test that finds the description has confirmed the claim was made, not that it is true.** It is the refusal entry above turned inside out. There, a test asserted that a refusal was *printed* rather than that the refused thing was absent. Here, five screens printed a *capability* and nothing asserted the capability existed: admission said a DNAR form "can be filed here" with no upload control; it labelled Contact and GP required with nothing in it required, over steps that gated nothing; the invite drawer said to change a person's role on a page with no role control; Settings said custom domains "are added" with nowhere to add one; the invitation asked for a job title and kept it nowhere. And behind a screen that looked finished, no screen could record a consent at all. **1,310 tests, and not one caught them.** The reason first written here was that the tests assert what the screen renders and the screen rendered the claim, and it was checked afterwards against the committed tests: that is true of one of the five. Admission's test found the DNAR sentence and passed over a step with no control. The other four had no test touching them at all: no test read the step strip, the invite drawer's sentence, the custom domains note or the job title field. For four of the five the answer is not "a test asserted the claim" but "nothing looked". **The tell is a sentence in the UI naming an action with no control beside it** — and its mirror, a field that accepts input and hands it to nothing.
  **How they got there matters more than any one of them, and there were two failures, not one.** Each was written as done: the sentence went in with the intention, the control did not, and each phase was reported complete. And **nothing asked** — each report was confirmed on the word of the report, the same thing as Phase 23, where a plan in conversation was taken as a phase in the history. A claim that nobody is positioned to contradict is not verified by being repeated back.
  **Whether it is checkable was costed, and it is not.** A search for UI copy promising an act — "can be filed", "are added", "on their own page", "can be recorded" and similar — found ten matches: three real defects and seven false ones, conditions ("before this can be recorded"), negations ("nothing can be recorded yet") and a screen describing itself. It would have missed two of the five outright, because a mislabelled step and a field that stores nothing contain no promise phrase. And the phrase list was written by somebody who already knew the answers, so its reach on wording nobody has seen is unknown and certainly lower. Seventy per cent false alarms from a list tuned to the known cases is wallpaper on the first run, and "nothing in the same component performs it" cannot be the discriminator either, because a legitimate statement often points at a later step or another screen. So it stays a question, asked where the sentence is written: **what control does this sentence promise, and is it within reach of the reader?** The only mechanism that caught these was checking each claim against the code while writing an account of them.

- **An explanation that fits the evidence is not the explanation, and the moment to check it is before it is written down.** The entry above first said the five defects got past 1,310 tests "because the tests assert what the screen renders and the screen rendered the claim". It is a good explanation. It matches the class, it matches the refusal entry it inverts, and it was written into this file without being checked against a single test. Checked afterwards, it holds for one of the five: admission's test found the DNAR sentence and passed over a step with no control. **The other four had no test touching them at all.** Nothing read the step strip, the invite drawer's sentence, the custom domains note or the job title field. "A test confirmed the claim" and "nothing looked" call for different repairs, and the recorded one was the more interesting and less true of the two.
  **How it was caught is the entry's subject.** Nothing in the build found it. It survived being written, being read and being agreed with, and it was caught only when a message credited its author with having verified it: with checking the reading, finding it wrong for at least one defect, and refusing to make the claim. None of that had happened. Going to look rather than accepting the credit is what turned up the four untested defects. **A wrong explanation, plausible and written down, survived until somebody was praised for verifying it.** The same message also handed back a guard scope, eight verbs and eight nouns, as the author's own. It had been invented while reading an entry that said the thing was not checkable. Attribution drifts the same way explanations do: a claim repeated back under somebody else's name reads as confirmed.
  **The tell is that the mechanism can be stated without naming the file.** "The tests assert what the screen renders" names no test. An explanation that cannot point at the line it is about has not been checked against that line, however well it fits. The cost of pointing is a `git grep`; the cost of not pointing is a record that sends the next repair to the wrong place.
  **And the other half, as Frank wrote it.** He confirmed the five screens as done on the report and asked nothing, twice now: Phase 23 was the same, a plan taken as a phase. **A third time in Phase 29**: a test run that could not finish was explained as memory pressure on the machine, and he agreed it was probably right on the report alone — the explanation had been offered on symptoms, and it was a render loop in code written that afternoon. **A report is a claim, and confirming one without asking what backs it is how a wrong claim becomes a shared fact.** Both halves are needed for this failure. A report written ahead of its evidence does no harm if somebody asks what backs it, and confirming without asking does no harm if the report was earned. Here neither happened.

- **A record that is a list, exercised only ever with one member, hides every defect that needs two.** Family access held a list per resident from Phase 21, and every test named one person. The store built each id from `members.length + 1`, so the sequence that breaks it needs three acts nobody had performed: name two, remove one, name another — and the new person carries an id already in use. Remove then deletes whichever holds it first, which is a screen taking access away from the wrong member of somebody's family while telling the reader it removed the right one. Nothing was wrong with the id of a first member, and a suite that never names a second cannot reach the state where anything is.
  **The fixture half is the same failure.** No fixture named anybody at all, so every screen over that list rendered its empty case in every test and on every load — including a queue whose finding would have been the whole population, every time. §8 already says a fixture has to reach every state a component renders; this adds the shape that hides it, because a collection looks exercised when one element goes through it. **The tell is a plural in the type and a singular in every test**: `FamilyMember[]`, `grantAccess` called once per test, no removal followed by an add anywhere. Where a record is a list, the cheapest test that is worth anything names two, removes one, and adds a third, then asserts who is left **by name** rather than by count — a count of two is satisfied by the wrong two.

- **A lookup keyed by `string` cannot miss, so it fails by printing nothing.** The consent badge rendered how a consent was given from `const METHOD: Record<string, string>` whose keys were `verbal`, `written` and `digital`. `ConsentMethod` is `'verbal' | 'written' | 'digital_signature'`, so every consent given by signature rendered **"undefined"** beside its date, on the badge whose entire job is to say what was decided and how. Three rows on one resident's Consent tab said it, and the build had been green for phases: nothing throws, nothing fails a type check, and the map's own type invites any key at all.
  **`Record<string, T>` is the shape to distrust wherever the key is a closed union.** Typed `Record<ConsentMethod, string>`, a member the map has not got is a compile error, and a member renamed in the union breaks the build rather than a screen. The nearby variant is a `?? value` fallback on the same kind of map, which does not print `undefined` — it prints `digital_signature` at a reader, which is the same defect wearing better clothes. **The tell: a map from a union to a label, typed by `string` on either side.**
  And the compile-time fix is only half of it. A map that covers every member proves nothing about what reaches a screen, so the other half is a test that renders each member and asserts the label is there — with the date stripped out first, because a badge that prints only its date passes any check that merely looks for text.

- **A value drawn from a pool lands on a subject, and the pool has to know which subject.** Every refusal in the fixtures took its reason from one list of three sentences, picked at random with no reference to the consent being refused. So "she does not want her picture anywhere" was recorded against medication administration, data sharing twice, medical treatment twice and care and support — while **photography, the one type it fits, never received it once**. All 57 refusals were drawn that way; the other two sentences said nothing in particular, which is why exactly one of them announced itself and the rest read as records.
  It is the pronouns defect in another field: a generated value landing on a subject it was never about. What makes it worse than a wrong pronoun is that a refusal reason is *evidence* — the record says somebody refused something for a reason they never gave, and nothing on the screen distinguishes it from one they did.
  **The tell is in the distribution, not in the rendering**: print the pairs of (subject, generated value) and look for the one pairing that ought to be common and is absent. A reason that fits exactly one type appearing on five others, and never on that one, is what a shared pool looks like from the outside. The fix is a pool per subject, drawn by the subject's own key — and where the generator draws once either way, the seeded stream does not move, so nothing else in the fixtures shifts.

- **A fallback correct for the common case is not a default, it is an assumption.** The session picked the active home as `sites.find(id) ?? sites[0]` — the first home that exists, not the first home the viewer holds. For an admin covering both, and for anybody at the larger home, that is the right answer, which is exactly why nobody found it: the uncommon case does not fail loudly, it produces a plausible wrong answer, and every check downstream agrees because nothing downstream can tell. It is the same family as the seeded draw landing on the wrong resident and the font file naming itself wrongly — correct-looking output from a wrong source.
  **The tell is the fallback's subject.** `?? sites[0]` answers "a home", where the question was "a home this viewer is appointed to". Where a default stands in for a scoped value, ask which set it is drawn from: the general one is an assumption wearing a default's clothes, and it is right often enough to survive review.

- **An effect that returns a value has declared a cleanup, and React will call it.** Four tests failed with `TypeError: destroy is not a function`, thrown while unmounting, and the assertions inside them had never run: the harness was `useEffect(() => onRead(...), [...])`, whose arrow body returns whatever `onRead` returns — here the number from `Array.push`. React takes an effect's return value as its cleanup function and calls it on unmount. **The suite died tidying up after a test that had not been performed**, which reads as a broken component and is a broken test. It is the test-that-cannot-fail family arriving through a framework convention rather than through a missing assertion, and the fix is one pair of braces. The tell: an effect written as a concise arrow whose call returns anything at all.

- **A busy process and a hung one look identical from outside, and high CPU is not proof of progress.** This entry first said a twenty-six-minute test run only *looked* hung because its output was buffered behind `grep | head`, and that the run was alive because its workers sat at 150% of a core. The pipe did buffer. The run was never going to finish. `SessionProvider` had begun memoising the viewer's homes on the sign-in itself, which takes a fresh timestamp every time, so the array changed identity on every sign-in; the test helper that signs in re-ran whenever that array changed, signed in again, and got a new array again. Every test that signed in spun in that loop until its worker exhausted its heap — at 4 GB, when the heap was raised to test the next wrong theory, "memory pressure on the machine". Stale workers with seventeen hours of CPU time were the same loop, still running.
  **The CPU reading was the loop, and it was read as the opposite.** Elapsed time and CPU say a process is doing *something*; they cannot say whether that something converges. What would have said so is cheap: whether any unit of work has *finished* — here, whether a single test file had reported — against how long a unit took the last time it ran clean. The suite's whole test stage took 47 seconds that morning; no file finishing in ten minutes is not slowness. **The buffered pipe mattered by making the wrong reading available**: with no output to read, the process list was the only instrument, and it answered a question nobody had asked.
  Two corrections came out of it, both about explanations adopted because they fitted: the buffering, then the machine's memory. Each was offered on the evidence of a symptom and accepted — the second by Frank, on the report, without asking what it rested on — which is the third occurrence of the entry above about confirming a claim without asking what backs it. **The tell for this family is a diagnosis that moves with each new symptom while the change that preceded all of them goes unexamined.** Here that change was one `useMemo` dependency, made the same afternoon the runs started failing.
- **A session ends in more ways than signing out, and state set for a session has to end with every one of them.** The viewer pointer was cleared in `endSession()`, which sign-out calls, and that was the whole of the rule as written. Tests end sessions differently: testing library unmounts the provider, nobody signs out, and the module-level pointer survived into the next test — which signed in as nobody and was refused another home's handover as a senior carer who had left two tests earlier. **Anything module-level that a component sets is owned by that component's lifetime**, so its cleanup belongs in the component's unmount as well as in the explicit exit. The tell is state whose writer is a component and whose only eraser is a user action.

- **A reachability guard finds a link, not a visible one.** The organisation setup wizard had a route, a link to it from the Settings tab, and a test asserting the link existed and pointed at `/settings/setup`. All of it was true. The link sat inside the grey subtitle under the tab's heading, the same colour, size and weight as "Rosewood Court." above it, with no underline, and the person the wizard was built for signed in, opened Settings and could not find a way in. **An element the reader cannot identify as clickable is unreachable in the only sense that matters**, and no crawler or DOM query can tell the difference: a link drawn as body text and a link drawn as a button are the same `<a href>` to every mechanism in this build. It is the donut and the hatched tile again, right assertion and wrong medium, arriving at navigation rather than at a figure. The repair was a control that looks like one — the button primitive's classes on the link, at the top of the tab for the thing it sets up — and the test now holds what jsdom can hold, which is that the control is the button primitive and sits ahead of every section; **whether it reads as a way in is a screenshot's question, and that is where it was checked.** The tell is a way into a screen whose styling comes from the text around it rather than from a control: `<p className={subtitle}><Link>` is a sentence with a destination, not a button.
  **The same screen carried a second defect of the same shape.** The page title read "Settings", the tab under it "Settings", and the heading inside the tab "Settings": three elements claiming one name, so the screen could not say what it was. And the tab mixed three scopes under that name — one home's name and timezone, figures held once for every home, and the wizard for the whole organisation. It is now a home tab headed by the home's name and an organisation tab headed by the organisation's, and a test asserts the page title, the active tab and the tab's heading are three different strings.
