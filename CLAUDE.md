# CLAUDE.md — diGi-Care

Rules that hold in every session. Read `FRONTEND_PRD.md` for the full spec; this file is the short list that must never be violated, whatever the task looks like.

**Project:** diGi-Care — care management platform, desktop manager app, frontend only. No backend, no API, no auth. All data from typed fixtures in `src/data/`.

**Stack:** Vite 8 · React 19 · TypeScript strict · React Router 7 (data router API) · Radix primitives (hand-authored) · plain CSS + CSS Modules over custom properties · `vite-plugin-svgr`.

---

## 1. The Evidence Invariant — the rule this product exists to protect

**A blank must never be able to mean either "no" or "nobody has looked yet".** In a regulated care record those are opposites. Everything below follows from that.

- **No clinical or compliance status is optional.** Every one is a closed discriminated union with an explicit unrecorded member. No `status?:`, no `| null`, no `| undefined`, no default parameter standing in for a missing record. The compiler must reject a screen that forgot the unrecorded case.
- **Unrecorded gets the hatched treatment** (`--status-unrecorded`, dashed border, diagonal hatch) plus visible text saying what is missing. Never empty space. Never a solid neutral fill. Never a RAG colour.
- **A compound state renders as separate facts.** Given-but-no-second-signature is a green "Given" pill *and* a hatched "Second signature not recorded" — two facts, two treatments. Never merged into one pill with the gap in small print.
- **Recorded and unremarkable renders quietly.** A completed in-date review, "nothing due", "all assessed" — plain text, not a filled pill. Quiet is not hidden: the full record still shows, author and timestamp included. Never reach for this to calm down a *gap*.
- **A claim over a filtered set carries the filter, or it is false.** A gap marker inside "Medication notes only" asserts an absence that is an artefact of the view. Suppress the claim or name the filter.
- **A recorded negative is not an unrecorded value.** "Not Given — resident refused — signed 08:04" is a complete record and looks settled. An omission looks unfinished. Never the same treatment.
- **Every aggregate carries its denominator.** No bare counts, no bare percentages, anywhere. Use the `Aggregate` type. Where coverage is too thin to support a claim, render **Insufficient Evidence** — which is not a milder Red, it is the absence of a finding.
- **Absence from a list is the same bug as a blank cell.** All ten risk assessment templates are listed even if none is completed. All eight consent types. All care plan domains.

If you find yourself writing a fallback like `?? 'Low risk'`, `|| 'None'`, `?? 0`, or `?? '—'` for anything clinical or compliance-related, stop. That fallback is the bug this product is being built to prevent.

## 2. Wrong-subject writes

- Every write surface carries a persistent, non-collapsing subject header: resident photo, name, preferred name, room, DOB.
- Subject identity comes from the route parameter. Never from navigation history, "last viewed", or component state.
- Confirmation dialogs name the subject in the sentence. "Record 08:00 medications for Emmanuel Okafor?" — never "Are you sure?".
- Active site name is always visible in the header, including for single-site users.

## 3. Icons

- **No icon library. Ever.** Do not install `lucide-react`, `react-icons`, `@heroicons`, or any equivalent, for any reason, including "just for this one icon".
- Icons come from the Aligned Line Icons set in `src/assets/icons/<CATEGORY>/` (3,559 SVGs, ~40 category folders). Never hand-edit those files.
- **Names are namespaced by category** because filenames repeat across folders: `<Icon name="add-remove-delete/add-01" />`, not `<Icon name="add-01" />`.
- Build step normalises used icons to `currentColor` so they take colour from CSS, then SVGR compiles them.
- `npm run icons` generates both `registry.names.generated.ts` (full name union, types only) and `registry.generated.ts` (import map of **only the icons actually used**, found by scanning source). Importing all 3,559 would bloat the bundle.
- **Never hand-type, hand-edit, or hand-extend either generated file.** A name not present in the folder fails the build.
- Re-run `npm run icons` after using a new icon name. It is wired into `predev`/`prebuild`.
- One `<Icon name="..." />` component. No raw `<svg>` in feature code, no direct imports from `src/assets/icons`.
- If a needed icon is not in the folder: **stop and ask.** Do not substitute an inline SVG, an emoji, a character glyph, or a similar-looking icon.

## 4. Colour and type

- **Colour only from tokens.** No hex, `rgb()`, `hsl()`, or named colours in any component. Colour reaches a component only as `var(--token)`. `src/styles/tokens.css` is the single exception and the only place a literal may appear.
- Stylelint enforces this and must stay in CI and pre-commit. Do not disable, weaken, or add exceptions to that rule.
- **Each status has a bright fill token and a darker ink token.** `--status-X` is for fills, dots, bars, borders and icons. `--status-X-ink` is for text on a tint. Using the fill token for text fails contrast and is a review blocker.
- **The type scale is closed.** Nine steps, five weights, all in `tokens.css`. No component introduces a size, line height or weight outside it. A tenth step is a conversation, not a local override.
- No dark mode. One palette. Do not add theme switching, `prefers-color-scheme`, or a `.dark` class.
- Spacing is the 4px scale only. No off-scale values.

## 5. Primitives

- **Do not run the shadcn CLI.** It installs `lucide-react` and overwrites the stylesheet with its own tokens — both break rules above. This is known; it does not need rediscovering.
- Primitives are hand-authored in `src/components/primitives/`, thin wrappers over Radix, styled to our tokens from the first line.
- Reading shadcn source as a reference for Radix composition is fine. Copying its stylesheet, token names, or dependencies is not.

## 6. Conventions

- **One shape, one meaning.** Underline strip = navigation. Pill = filter. Two concepts in one treatment is the same defect as one concept in two; "they never appear on the same screen" is not a defence, because a reader learns the shape rather than the screen.
- **Segmented control = one of a small set of mutually exclusive presentations of the same data.** Week/month on the MAR chart is an instance, not the definition; calendar/list on the activities week is another. Widened deliberately rather than adding a fourth shape.
- **A value whose correct rendering depends on where it appears cannot be rendered by whoever happens to be appending it.** It gets one owner, and the call site asks that owner. Six so far, each found the same way — `quantityWithUnit` (stock, depends on the count: "1 patches"), `pluralise` (a plain count: "1 days"), `scoreText` (a union member: "[object Object]"), `INCIDENT_TYPES.phrase` (a label that reads correctly in a column and wrongly in a sentence: "the fall — witnessed of 23/08"), `formatLateness` (how overdue, depends on the size: "426 days late"), `formatAttributionOn` (who and when, depends on how old the record is: a draft from last Tuesday rendered as "11:29").
  "1 patches" and "1 days" were each written twice in independently authored files — not typos, but what happens when a formatting rule has no owner, and the second occurrence proves there will be a third. **The last is the sharpest**: time alone is correct for a record read on the day it was made — a dose at 08:04, a note from this shift — and every use of it until this one was that kind of record. A rule that was right for every case it had met is the hardest kind to notice going wrong.
  **The tell, twice now: a test that has to be relaxed to let a correct change land was pinning the rendering rather than checking the property.** `/days overdue/` asserted the *unit* in order to check that a duration was stated at all.
- British English in code and UI copy. `Organisation`, `Authorised`, `Finalise`.
- Dates `DD/MM/YYYY`, times 24-hour. Relative time only alongside an absolute timestamp, never instead of it.
- **Clinical timestamps render in the site's timezone, never the viewer's.** Show the zone label where ambiguous. Relative time is the exception — it is about now, not the record.
- Every clinical record shows its author and timestamp. Always visible, never hover-only.
- Care notes are immutable after submission. There is no edit control. Corrections create a new linked note.
- No `any`. No `@ts-expect-error` without a comment naming what removes it.
- No `localStorage` / `sessionStorage` for record data. In-memory only.
- No placeholder or lorem text. No `console.log`. No commented-out code.
- Fixtures stay messy on purpose — missing assessments, omissions, thin sites. Do not "clean up" fixture data to make a screen look better. The gaps are the test.

## 7. Accessibility

- WCAG 2.2 AA. Colour never the sole carrier of meaning. Visible focus ring, never removed.
- The MAR grid is a real `<table>` with header associations and full-sentence accessible names per cell.
- Icons are `aria-hidden` unless labelled. Icon-only controls need a visible adjacent label or an `aria-label` plus tooltip.

## 8. Standing checks

These have each caught a real defect more than once. Run them rather than rediscovering them.

- **Every state a component can render needs a fixture that reaches it.** `latestNote: 'none'` shipped in three places for a resident who could not exist; "All assessed — no flags" went dead silently; the `on_file` photo branch was never rendered. If no fixture reaches a branch, either the fixture is wrong or the branch is.
- **An assertion you edit each phase to make it pass has stopped asserting.** A hardcoded count of disabled nav items measures the work, not the rule. Derive it from the declaration.
- **A comment claiming a guarantee is a claim to verify, not documentation.** Ten were found overstated in one sweep — each named a real mechanism that enforced something narrower than claimed. The ones that held had a test behind them.
- **Volume that drowns a distinction is the same failure as a blank cell.** 303 omissions where three were specified; a chip that fires on every row; markers on half a timeline. Check the count, not just the rendering.
- **A fact you intend to derive is only derivable if the record keeps what it is derived from.** `ReviewState.completed` carried the date a review was done and the date the next one falls due, and not the date it *had been* due — so "reviewed on time" and "reviewed three weeks late" were the same record, and the lateness was not hidden but absent. **And what it is compared against may not exist**: a review nobody ever scheduled can still be done, and it had no deadline to beat. Inventing one produces a lateness nobody can check, so the field is a union — a date, or a statement that there was never one. Same shape as a controlled drug count with no opening balance: the comparison has two inputs, and the missing one is a state rather than a zero.
- **A clamp or conversion written for one kind of instant will silently corrupt another.** `dueBy` is a deadline, `signedAt` is a signature, `recordedAt` is an observation — all three are `IsoDateTime` and the compiler cannot tell them apart. A helper that exists to stop a *signature* landing in the future, applied to a *deadline*, dragged every post-incident review flag back to this instant: the whole set read as overdue and the constant named `FLAG_STILL_IN_TIME` was not still in time. That is the reassuring-branch problem in reverse — it manufactured an alarm rather than hiding one, and a false alarm on every row costs the same as a hidden gap, because both teach the reader to stop looking. **The tell: before applying any transformation to a timestamp, say out loud what kind of instant it is.**
  **This entry is no longer the mechanism either.** It sat here from Phase 7 and the class landed three more times: `filedOn` widened to midnight and rendered through the site's zone as "02/10/2025 01:00 BST", and a review's `dueOn` doing the same on the Dashboard — "01:00 BST" against every overdue review on the screen. So `scripts/check-instant-kinds.mjs` enforces the half of it that is mechanical: a date widened into an instant by string concatenation is a finding **unless it is consumed by `new Date(` on the same line**, which is arithmetic. `// instant-ok: <why>` opts out per site and the count is printed. It does not catch the original clamp — a function applied to the wrong kind of instant is not a string shape — and saying so is part of the entry: **the tell still has to do the work for that half.**
- **Fixtures may be wrong on the facts, not just thin.** One to three care notes a day is not a patchy home, it is a home that does not exist. Correcting a wrong baseline is not tidying up gaps — the deliberate gaps stay exactly as they are.

- **What has already happened to this record before somebody opens this screen?** The fixture check above covers states of a component; this covers states of the record a screen edits — part-recorded, recorded by somebody else, superseded. On any screen more than one person touches, part-recorded is the ordinary state and empty is the rare one, so a suite written entirely against empty is testing the exception. A dose already signed for once rendered as an empty control, inviting a second signature over somebody else's name.
- **An assertion that has to be relaxed to make a legitimate change was testing the wrong thing.** "Exactly three omissions in the whole set" was asserting a property of the home in order to check a property of a fixture. Hold the specified case by reference, never by a number that legitimate data would move.
- **An assertion written from the same string or the same assumption as the code confirms the bug rather than catching it.** The "4 hours threshold" wording, and the round's `balance - 1` arithmetic, were each asserted from the same mistake they contained. Assert the behaviour, not the literal you just typed.
- **An assertion satisfied by an equality is not asserting a margin.** `flagIsOverdue` is `dueBy < now`, which is false when the two are equal — so a review flag with *zero seconds left* counted as one somebody could still do on time. The guard was green and the fixture had no in-time flag in it at all. Where a test means "with room to spare", it has to say so: a boundary is the one place a broken mechanism and a working one give the same answer.
- **A proxy for a rule is a second rule, and two rules drift.** A test asked a hand-written approximation of the "all assessed, no flags" condition — four of the six things the cell actually checks — and the approximation stopped being satisfiable while the real condition still was. **It failed on a screen that was working**, which is the direction that gets working code changed to satisfy a broken test. It drifts the other way too, and then it passes while the branch it protects goes dead; the failure looks different each way round while being the same defect. The fix is the same in both directions: **assert through the thing itself**, never a hand-written approximation of it. Export the predicate the screen uses and have the guard call it.
  **A second occurrence, from the other end: reproducing a rule is the same defect as approximating one.** The Dashboard needed to know which days a drug falls due on, so the helper was written by reading the fixture generator and restating its arithmetic — faithfully, except for a `Math.min(…, 89)` clamp, one token, that anchors the schedule to the first day on the chart rather than to the prescription date. Two counts of the same doses today, 162 and 163, from two functions written minutes apart. Neither was obviously wrong and nothing failed; what found it was printing both numbers next to each other. The generator now exports the constant and both sides read it — a copied formula is a second rule even when it was copied correctly, because the original is still free to move.
- **Any test whose result derives from `now` gets a pinned instant and a sentence saying why, when it is written.** Not after it fails. This has caught the same class three times: green all day, red at 04:42, and in one case the screen was right and the assertion was wrong. The cost is one line; the failure mode is a suite that is green for you and red for whoever runs it next, which reads as flakiness and gets retried rather than read.
- **A suite that goes green on the first run of new tests deserves a look at whether the tests can fail.** Three times now this instinct has found something. `expect(after.items.length).toBeGreaterThan(0)` was asserted on the *unpatched* fixture — true before the act it was testing and after it. `rows.length % 10 === 0` is true of ten, of twenty, and of zero. Neither could fail, and both read as coverage. Pick the two or three assertions carrying the most weight and break the code under them on purpose.
- **A query must name the element it means, specifically enough that nothing else can satisfy it.** `queryByRole('button', { name: /Acknowledge/i })` matched the "Not acknowledged" filter pill; `container.querySelector('ul')` matched the profile header's risk flags list; `container.querySelector('[data-state="recorded"]')`, meaning the allergies badge, took whichever badge a fixture shift put first. The polarity was never the point — a **positive** assertion reaching for a loose selector fails in the more dangerous direction, passing on the wrong element rather than failing on the right one.
  **This entry is no longer the mechanism.** It sat here from Phase 4 and did not prevent a single one of the recurrences, so `scripts/check-selector-specificity.mjs` enforces it in both polarities: a query rooted on the document or on `container` in a router test must be scoped to an element the test chose, or name its target with an attribute selector, an exact string, an anchored pattern, or three words. `getBy`/`findBy` are exempt because the library already throws on an ambiguous name; an un-indexed `…All…` query is exempt unless it claims the sweep found nothing. `// selector-ok: <why>` opts out per site and the count is printed.
  **The general rule, and it applies to every entry here: a standing check that has not prevented a recurrence after three tries is not a check, it is a note.** Either it becomes enforceable or it stops being counted as coverage.
- **One class here is uncovered, and is written down as uncovered rather than given a mechanism that reads as coverage.** A selector naming a *condition* where the test meant an *identity* passes the check above, because it does name an attribute: `container.querySelector('[data-state="recorded"]')`, meaning the allergies badge, is specific and still wrong. Deriving condition attributes from the source — those emitted with two or more distinct literal values — separates `data-state` and `data-finding` from `data-badge` and `data-field` correctly, and then calls `data-tally-cell="invited"` a condition, which it is not: there the condition **is** the identity of the cell. That produced 85 findings with legitimate cases among them, and a guard needing 85 escape comments is wallpaper inside a week — the exception-list failure named two entries above, arrived at from the other direction. The tell is the whole defence: **before selecting on an attribute, say whether it names which element or what condition it is in.** If it is the condition, the query takes whichever element the fixture happened to put first.
- **Knowing an entry does not inoculate you against it.** The Dashboard's date-kind guard asserted that *at least one* row rendered a date, while every review on the screen was widened to an instant — the unsigned handovers satisfied it. That is the specificity defect wearing a positive, written minutes after the entry describing it, by the person who had just written that entry. **Familiarity is not the defence; the mutation is.** Break the code a guard was written for and watch it fail, every time — a guard that passes on the defect it exists to catch has not been tested, however well its author understands the class.
- **Ask whether a value means anything without the thing beside it, not whether the field is present.** The admission form asked what somebody is allergic to and what happens, and `Allergy` had always required a severity — so "rash and swelling" was not a field somebody forgot, it was **a fact with its other half missing**, and it reads as complete because both words are there. A presence check finds nothing here; the question that does is whether the value can be acted on alone. It could not: the difference between mild and anaphylaxis is whether that person carries an adrenaline pen. **The same test finds the next one** — a dose with no unit, a score with no band, a count with no denominator, a negative with no source.
- **Rendering everywhere is not coverage.** A value on six screens looks proven by its ubiquity and is the most likely thing in the build to be unasserted, because nobody writes a test for something they see constantly. "(deactivated)" rendered beside authors in six modules and exactly one test touched it — a unit test on the formatter, not a screen. Changing where it came from altered twenty-three files and broke nothing. **The tell is a change that touches many files and breaks nothing: that is not confidence, it is silence.** When a refactor comes back green faster than it should have, go and find what was supposed to have caught it. **Second occurrence, one phase later**: the sidebar alert told every screen that "the Reviews module arrives in a later phase" for nine phases after Reviews shipped. Nothing caught it, and nothing could have — it was true when written, it renders on every screen, and it is exactly the string everybody has stopped reading. Ubiquity is what makes staleness invisible, not what protects against it.
- **A figure that needs a note explaining how not to read it is a figure whose existence to check.** The staff report carried a "doses with no record" column beside a note warning that a gap in the record is not necessarily a failure by whoever was on shift — and an omission is a dose *nobody* recorded, so it carries nobody's name at all. The note would have read as a disclaimer on a column that could not honestly exist. The same shape one step in: "0.0%" against somebody who worked no rounds is a denominator that supports a rate perfectly well and an accusation all the same. **The tell: when a screen needs prose to stop a reader drawing the obvious inference, ask whether the figure belongs there rather than writing better prose.**
- **A string transformation that reads as tidying can destroy the thing being tidied.** `.toLowerCase()` on the field label "What I need help with" produced "what i need help with" — a label written in a resident's own voice, with the one word that is the point of it removed. It is the same move as agreeing a plural at the call site: **a value whose correct rendering depends on where it appears cannot be rendered by whoever happens to be appending it.** "Fall — witnessed" is right in a column and wrong in a sentence, so it carries a name and a phrase rather than a `.toLowerCase()` at each use.
- **A screen that cannot be reached from the navigation is not built, however green the tests are.** Guards run bidirectionally — every route has an entry, every entry has a route. The MAR chart passed 517 tests while being unreachable.
- **A refusal that rests on a figure stops being a refusal the moment the figure moves.** The compliance overview states that there is no overall compliance percentage and never will be. The reason it gave was "N of 5 Key Questions cannot be rated at all, so there is nothing to average" — and N was **zero**: all five were rated, so the screen's stated reason for refusing the figure was false on the day it was written. The hero carried the same defect one size larger, in the largest type on the screen: "0 of 5 — Key Questions unratable **as a result**", a causal claim over four unusable checks that had in fact left every panel ratable, and a zero reading as reassurance in the one position reserved for the opposite. The refusals in this file are standing properties, so their stated reasons have to be standing too — averaging ratings taken over unrelated populations is one, a count that happens to be non-zero today is not. **The tell: if the sentence explaining a refusal contains a number, ask what the sentence says when that number is zero.**
- **A repeated segment in a rendered string is two owners agreeing the same fact.** The pharmacy cycle printed "30mg · 30mg · capsules" and "75 micrograms · 75 micrograms · tablets", because `Medication.form` is *form and strength as the register lists it* and the row put the dose in front of it. Neither half was wrong; the second one did not know the first existed. This is the one-owner rule with a tell attached that does not need the owner to be known in advance: **read the string back and look for a value stated twice.** It found this in a screenshot in under a second, where reading both field definitions would not have — `dose` and `form` are both strings, both plausible on a medication row, and the docblock explaining that `form` already carries the strength is four hundred lines away from the call site.
- **Lowercasing a constant you wrote is safe; lowercasing a value out of a record is not.** The document viewer rendered "a representative dnar form", from `document.title`, which is a title somebody typed into a record. The §8 entry above about `.toLowerCase()` destroying a label was written a phase earlier and did not prevent it — second occurrence, same transformation, different field. The distinguishing question is where the string came from: `SHIFT_NAMES[shift]` and a consent type's `name` are closed vocabularies whose casing is ours to choose, and a document title, an allergy's reaction, a resident's own words are not. A mechanical guard was written and thrown away: 30 sites lowercase into JSX and roughly 27 are legitimate, so it would have needed 27 escape comments and been wallpaper inside a week — the exception-list failure this file already names, arrived at for the third time. **What is enforceable instead is the question, asked at the call site: is this string one we wrote, or one somebody recorded?**
- **Before counting what relies on a record, ask whether two of them are the same fact stored twice.** The document viewer's rail said "3 records rely on this document" for a DNAR that two of the three reached through the same field: a resident's resuscitation decision is held on the resident and mirrored under future plans, and the fixture builds the second from the first. Two readings of one field break together, so the honest count was two. This is a denominator inflated from inside the record rather than from a wrong population — the aggregate rule one level down, where the duplicate is not a duplicate row but a duplicate *route to the same row*. **The tell: when a list of referrers has two entries pointing at the same screen, say whether they would break separately.**
- **The complement of a population is not automatically a gap.** A chart bar read "213 of 306 documents in date", and its hatched segment therefore claimed 93 records "nobody has written" — but an expired document *was* written, by somebody whose name is on it. That is Rule 3 (a recorded negative is not an unrecorded value) appearing in an aggregate rather than in a cell, where it is much harder to see: the cell version is one wrong badge, the aggregate version silently recruits every recorded-but-unwelcome answer into the missing-evidence count and inflates it. The fix was to count the thing that genuinely has an unrecorded state — documents carrying an expiry *decision* — and being out of date went back to being a finding. **Before hatching `total − recorded`, say what the remainder actually contains.**
  It came with the one-owner rule attached: the same population needs **two phrasings**, because "42 consents sought" against a missing count reads as forty-two consents that were sought. The bar says `population`, the missing list says `missingPhrase`, and neither call site agrees the wording itself.
- **A guard blind to a second medium is not a guard, however green it prints.** `check-hatch.mjs` exists because the hatch is the most load-bearing visual in the product and a second, slightly-different copy is the drift that survives review. It read `.css` files, which was the whole world until the Dashboard's charts needed the hatch as an SVG `<pattern>` — a chart area and an arc stroke cannot take a CSS background. The rule was never violated and the mechanism covered nothing: a second `<pattern>` anywhere would have shipped under a tick that said the treatment had exactly one definition. **The tell: when a concept gains a new medium — a new file type, a new renderer, a new output — every check that names that concept is now narrower than its own success message.** The check either learns the medium or its message has to stop claiming the concept. This one learned it, and the message now says *per medium*.
- **A chart can be accurate and unreadable, and the fix is never the axis.** The area chart plots doses recorded against doses due; this home records about 98% of them, so the hatched gap between the two lines is three per cent of the chart's height — drawn exactly to scale, and invisible. The tempting repair is to start the y-axis near the data. **A truncated axis magnifies a gap by hiding zero, which is the reassurance failure run backwards** — alarming rather than soothing, and the same lie about proportion. It belongs with `FLAG_STILL_IN_TIME` above, which manufactured an alarm on every row: a false alarm and a hidden gap cost the same, because both teach the reader to stop looking. **The geometry stays honest and the figure gets printed**, so a day on which six doses went unrecorded says six whether or not six pixels show it. Same move as the aggregate entry above: when a shape cannot carry a fact, the fact is not reshaped, it is stated.
- **A value can be in the DOM and painted over on screen.** An SVG circle with no `fill` declared defaults to black, so the donut arc that took its stroke from the hatch pattern laid a solid black disc across the middle of the chart — over "of 162 doses scheduled today", which is to say over the denominator. Every test passed, and **every test was right**: the string was in the DOM, in the right element, with the right numbers in it. That is the part worth holding on to — this is not a test asserting the wrong thing, which is what most of the entries above are about. It is a test asserting the right thing **about the wrong medium**. A suite that queries text cannot tell a figure from a figure nobody can see, so occlusion, contrast, clipping and z-order are a class no assertion in this build reaches, however well written.
  **So the read-back is a screenshot, not a DOM dump.** The dump was the method while there was no way to rasterise a page; there is one — the Chrome on this machine, `--headless --screenshot`, with `sips` for greyscale, and no dependency added to do it. Every screen carrying a graphic gets looked at, in colour and in greyscale, and the greyscale pass is the one that proves the hatch is doing the work rather than the hue. §3.6's midnight-BST calendar was found the same way and is the same lesson a phase earlier: it was found only by looking at a picture.

- **A value can be correct in the DOM, correct in its class list, and invisible on screen. Only a screenshot finds it. Second occurrence.** The first was the donut: an SVG circle with no `fill` defaulted to black and laid a solid disc over "of 162 doses scheduled today", with every test passing and every test right — the string was in the DOM, in the right element, with the right numbers in it. The second is the staff dashboard's hatched tile, which carried `composes: unrecorded`, rendered `data-state="unrecorded"`, and had a `className` matching `/unrecorded/`. Three assertions, all green, on a tile that painted as a plain white card: a shared `.tile, .tileNow, .tileWarn, .tileGap` rule set `background: var(--bg-surface)` and won on source order. **The second is the worse of the two and it is worth saying why.** In the donut something was drawn over the value; here nothing was wrong anywhere — the class was applied, the cascade simply resolved the other way, and there is no state in the DOM that differs between a tile that hatches and a tile that does not. A `composes:` is a claim about cascade, and cascade has no representation a query can reach. **So asserting the class name is not evidence the treatment rendered**, and the rule that follows is mechanical: a shared shape rule never sets `background` or `border` for a class that composes the hatch — shape in the shared rule, paint per tile.
- **A specific claim built on a false source is more dangerous than the vague statement it replaces, because specificity is what makes it trustworthy.** Signing out destroys everything in memory, so "unsaved changes will be lost" was replaced with a list naming each kind of record and its count — a claim a reader can hold against what is actually there, which is the whole argument for itemising it. The source chosen was the session activity log, whose docblock said every write in the product passes through one logging function. **Nine of the client's nineteen write functions never reach it**: every medication round, PRN dose, controlled drug opening count, review flag closed, care plan draft saved and every undo. A shift's medication records would have been destroyed under a list that never mentioned them — and the reader would have trusted that list *more* than the sentence it replaced, because it was itemised, counted and precise. **Vagueness fails safe; precision does not.** A sentence that says nothing in particular cannot be wrong about medication, and a list that names four things is read as naming all of them. So the question to ask before making a claim more specific is not whether the new claim is better, but **whether the source can carry the weight the specificity puts on it** — and the docblock asserting it could was written when it was true of the two call sites that then existed. `scripts/check-session-losses.mjs` now fails the build when a store in `src/data/access` holds session state and `session-losses.ts` does not ask it, which is enforceable because "holds session state" is a module-level mutable collection and that is a shape a script can see.
- **Testing that a cap is applied and testing that the cap is right are two different tests, and the first passes when the second would fail.** The permission ceiling fixed a whole class at once: each module declares the acts it offers, and a role's level is capped at what the module has. The guard asserted the property — no cell exceeds its module's ceiling — and it is a good guard, and it passes happily on a ceiling declaring that the Dashboard takes writes. **A property test over a derived bound inherits every error in the bound**, silently, because the bound is what the assertion compares against: the test and the defect agree by construction, so there is nothing left to disagree. It took two mutations to know that — remove the cap, and corrupt the cap — and only the second one is about whether the answer is correct rather than whether the machinery ran. This is the Phase 7 proxy entry arriving somewhere new. There it was a hand-written approximation of a rule drifting from the rule; here nothing is approximated and nothing drifts, and the failure is the same shape: **an assertion is only evidence to the extent that its reference could have disagreed with it.** So a property over a table is never the whole guard. The cells that were actually wrong get held by name as well — Dashboard and Reports are Read for everybody, stated outright — because a named case is the one thing a corrupt bound cannot absorb.
- **A permission matrix reads as a specification of somebody else's access, and showing it to its subject is the first time anybody checks it against what they actually do.** Sixteen modules by seven roles is 112 cells, every one plausible on its own, and it was wrong for fifteen phases: a care worker read "Record" against the Dashboard, where nobody writes anything, and a manager read "Approve" against Reports, where there is no work of anybody else's to sign off. Nothing found it, and nothing could — the manager's matrix describes other people, so a reader checks its shape rather than its claims, and a cell about somebody else's job is a cell nobody has the standing to contradict. It was caught the day `/me/permissions` put the same row in front of the person it was about. **The general form: a screen describing a third party is unaudited by construction, and the cheapest audit available is showing it to its subject.** The fix was not to correct the cells — a corrected table drifts the same way — but to declare what each module actually offers, naming the act, and cap every role at it. A guard asserts no cell exceeds its module's ceiling, and `levelFor` throws on a module with no acts declared, because an uncapped module is how "Record" got onto the Dashboard. The same pass found five exceptions naming `/team`, which stopped being a sidebar item in Phase 15: they narrowed nothing for anybody and still read as decisions somebody took.
- **An assertion guarded by a null check is an assertion that can stop running, and the fixtures decide when.** The invitation guard checked that the role and access render above the password fields — inside `if (password !== null)`, because the only invitation in the fixtures expired a month ago and an expired screen has no password fields. It passed by never running. Same shape as the round queue's `rooms.indexOf('—')` returning -1 for ever, arrived at from a different direction: there a copy change killed it, here it was born dead. **The tell is the null check itself**: ask what makes the value null, and whether any fixture makes it non-null. If none does, the branch under it is unasserted no matter how many times the suite is green.

- **A test that identifies a state by the characters it renders dies silently when the copy changes.** The round queue marked an unrecorded room with an em dash, and the guard for "unrecorded rooms sort last" found that row with `rooms.indexOf('—')`. When the dash was replaced with words, the lookup returned -1 for ever and the assertion under it — guarded by `if (unrecorded !== -1)` — simply stopped running. The suite stayed green, the count of tests did not move, and the rule went unprotected. This is the "assertion that cannot fail" entry arrived at from a new direction: the test was not written that way, **an ordinary copy change made it that way**, and nothing in the sweep that caused it had any reason to look at that file. Read a state off an attribute the component sets for the purpose, never off the glyph it happens to print. The same sweep is the reason: a house-style decision moves hundreds of strings at once, and every guard keyed to one of them fails open.

- **`toContain` on a sentence says the value is present, never that it is in the right place.** The late list's claim has to state the *filtered* count and the unfiltered total beside it, and the guard checked `toContain('late in total')` and `toContain(String(total))`. Changing the claim to lead with the unfiltered figure — the Rule 3c defect the guard exists to catch, a count of 26 sitting above a list of 3 — left both assertions true, because the total was still in the sentence; it was simply in the position the filtered count should have occupied. **This is the selector-specificity rule applied to text**: a substring match names a value the way `container.querySelector('ul')` names an element, which is to say not at all. The fix was to read the leading figure and compare it against the pill's own count, so the assertion says *where*.
  The mutation is what exposed it, and one alongside it makes the other half of the point: a second guard survived its mutation because two mechanisms protect the same outcome, and either one alone is enough. That is a guard being belt-and-braces rather than a guard being broken, and the difference is only visible by breaking both. **Neither case is distinguishable from a working guard without running the mutation** — which is the whole argument for running it every time.

- **Two halves of one question, answered to two clocks.** The donut's "due now" read the state baked into the MAR fixture at generation; "not due yet" beside it compared the round's wall-clock time with the home's. Both were defensible on their own and the pair was not: the fixture's instant is when the page loaded and the home's clock keeps going, so a round that opened while somebody had the tab open stayed *not due yet* while the header said otherwise, and one that closed stayed *due*. It read as a chart that would not update. **The tell is not that a figure is stale, because a stale figure looks like a working one; it is that two figures in the same set are computed from different sources.** Where a set of counts partitions one population, one derivation answers all of them or the set does not add up — and it will still add up to the total while being wrong about which bucket things are in, which is why the sum being right proves nothing here.

- **A figure that is correct and indistinguishable from broken is the worst pair on offer, and the fixture is usually why.** "Due now, inside its window" read zero on every load, and it was right every time: the generator recorded *every* round in the past, including one that had opened four minutes earlier, so no dose in the fixture was ever inside its window. The state was unreachable, and no amount of looking at the screen could tell that from a screen that had stopped updating. **A reader cannot distinguish a true zero from a dead one, so an always-zero figure is a defect even while it is accurate.** The check is the standing one about fixtures reaching every branch, and the reason it needs saying again: this branch could not be reached *at any hour*, because the fixture is generated at the moment of the load and the generator finished the round it was standing in. Where a fixture is built against `now`, ask what it makes true of *now* specifically — the states that only exist in progress are the ones it will quietly complete.

- **Spending the alarm vocabulary on something that is not a finding is how the alarm stops working where one is.** The moved-clock notice was built in `--status-caution`, with the amber border and tint a finding wears, and ran to four lines ending "nothing here is a record of what has actually happened today". Every word of that is true of every screen in this build at every hour, because the whole record is fixtures — so saying it loudly *only* where the clock has moved implies the rest is real, and puts a standing alarm on the front door for a thing nobody needs to act on. **A notice is not a finding, and the treatments are not interchangeable.** What a reader needed was the instant, why, and the way back, which is one quiet line. The tell is the same one as the figure that needs a note explaining how not to read it: if the prose is doing the work, ask whether the treatment is wrong rather than writing better prose.

- **A test can be satisfied by the wreckage of the act it tests.** The group overview's switch calls `setActiveSite` then `navigate('/')`, and its test asserted the overview was *still on screen* afterwards. It passed — because the memory router had no `/`, so react-router resolved against an undefined match and threw, and nothing moved. Had the button worked, the overview would have unmounted and the assertion would have failed. **This is worse than a vacuous test**: a vacuous test asserts nothing, and this one asserted the failure, so the defect and the green tick were the same state. Nothing could distinguish them from inside the suite; the unhandled rejection was the only trace, and it was in a file whose 16 assertions all passed. **The tell: an assertion that the thing under test is still present after an action whose whole purpose is to remove it.** If clicking is meant to navigate away, `expect(thing).toBeTruthy()` afterwards is a test of the crash. Assert both halves of the act — where the reader landed, and what the session did — and mutate each half separately, because one mutation would have passed on the other's assertion.
- **A slow test may be measuring a slow screen, which is the useful case.** `zonedWallClock` constructed a new `Intl.DateTimeFormat` on every call, and `withoutNoteToday` called it once per note — 11,125 constructions, 405ms. It surfaced as a 42-second test file, and the tempting reading was "tests are slow". It was never only a test cost: `zonedDate` is called in loops by the dashboard, the group figures, the MAR chart and the note series, so **real screens were blocking the main thread for 400ms on every load**. Construction is the expensive part of `Intl` — about 36µs against well under a microsecond to format with one that exists — so the fix was a cache keyed by shape and zone, not a smaller loop. **This is the argument against raising a timeout: the clock was the instrument, and reading it found a product defect.** A timeout raised three times had already hidden this once. Before raising one, ask what the number is telling you about the screen, and profile rather than guess — the same run also disproved two confident hypotheses (unpaginated rendering, simulated latency) that would each have sent the fix somewhere useless.
- **A flag typed once at a terminal is invisible to everyone who clones afterwards.** `--legacy-peer-deps` made this tree install for weeks and left nothing behind — no `.npmrc`, project or user. The first machine to run a plain `npm install` was a build server, which is where the ERESOLVE finally surfaced, long after the decision that caused it. Same family as an over-broad gitignore: **the state that matters lives somewhere nobody reading the repo can see.** A shell history is not a decision the project has made. If a command needs a flag, the flag belongs in a committed file — or the need for it does, as an `overrides` block that says which peer range is being disregarded and why.

## 9. Stop and ask

Ask before doing anything expensive to reverse. Frank is a product manager, not a developer — a wrong assumption costs him a rebuild, not a quick undo. Stop and ask before:

- Installing any dependency not already in `package.json`.
- Adding, renaming or removing a design token, or introducing a colour or type step.
- Changing the shape of a fixture type, especially a status union.
- Restructuring folders, routing, or the app shell.
- Changing anything in `FRONTEND_PRD.md`.
- **This file is the exception, and only for §8.** Standing checks are written here in place as they are found, because Frank's local copy does not carry them — handing one over would delete every check written since Phase 3, in the file that exists to prevent exactly that. New §8 entries are added and then reported. Wording for every other section comes from Frank.
- Deleting or rewriting existing working code to accommodate new code.
- Any workaround that would relax a rule in this file "temporarily".

When something in the spec is ambiguous or looks wrong, say so and wait. Do not pick the interpretation that is easiest to build.

## 10. Working cadence

- Build **one phase at a time**, in the order in `FRONTEND_PRD.md` §8. Stop at the end of each phase for review.
- In Phase 1, stop after **each screen**. From Phase 2, a full module per review is fine unless problems appear.
- Before starting a phase, restate what you are about to build and wait for approval.
- **Reports in chat are short**: what to look at, and anything needing a decision. Nothing else.
- **Bugs, reasoning, decisions, and anything discovered go in `PROGRESS.md`** — never in the chat reply. Append, do not rewrite history.
- Every screen is reviewed against all seven states before it is called done: Loading · Empty · Partial · Populated · Stale · Error · Read-only.
